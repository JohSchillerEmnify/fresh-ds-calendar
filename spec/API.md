# REST API contract

Served by `server/` (Fastify) under `/api`, consumed by `web/`. JSON only (`Content-Type: application/json; charset=utf-8`).
Types below are normative; the server validates requests with equivalent JSON schemas (Fastify `schema`), and the
TypeScript types live in one shared module (`server/src/api/types.ts`, copied or path-aliased into `web/`).

## Conventions

- **Time zone**: `TZ` env (default `Europe/Berlin`). All "date-only" values are local dates in that zone.
- **Timed values**: RFC 3339 with offset, e.g. `"2026-10-14T09:00:00+02:00"`. Server responses always use the
  calendar time zone offset. Requests may use any offset or `Z`.
- **All-day values**: `"YYYY-MM-DD"`. `end` is **exclusive** (Google semantics): a one-day event on 2026-10-16 has
  `start: "2026-10-16"`, `end: "2026-10-17"`. The UI shows inclusive end dates.
- **IDs**: opaque strings from the provider (Google event ids: `[a-v0-9]{5,1024}`). Task list item ids: 8-char
  `[A-Za-z0-9_-]` (nanoid) generated by the server.
- **Concurrency**: every item has an `etag`. `PATCH`/`DELETE` on events and task lists accept an optional
  `If-Match: <etag>` header. If present and stale → `412 PRECONDITION_FAILED`. The web app always sends it for event
  edits/deletes and task list detail edits. Item-level operations (`/items/...`) do **not** require it: the server
  re-reads the latest task list, applies the operation, and writes back with the fresh etag (retrying up to 3 times on
  a provider-side 412), so concurrent ticks from Google and the app merge.
- **Unknown fields** in request bodies → `400 VALIDATION_ERROR`.

## Error format

Every non-2xx response:

```ts
interface ApiError {
  error: {
    code: ErrorCode;
    message: string;              // English, may be shown to the user
    key?: string;                 // message key (web catalogue path), set for user-facing validation errors
    details?: { field?: string; issue?: string }[];
  };
}
type ErrorCode =
  | 'VALIDATION_ERROR'      // 400
  | 'NOT_FOUND'             // 404 (also unknown /api routes and /api/__test/* when TEST_MODE is off)
  | 'PRECONDITION_FAILED'   // 412 etag mismatch
  | 'PROVIDER_ERROR'        // 502 provider returned an unexpected error
  | 'PROVIDER_UNAVAILABLE'  // 503 provider unreachable / outage / auth failure
  | 'RATE_LIMITED'          // 429 only `POST /api/diag/sync-error`
  | 'INTERNAL';             // 500
```

`key`, when present, names a message of the web catalogue (for example `errors.validation.endAfterStart`); the web
app shows that message in the person's language and falls back to the English `message` for unknown keys.
Validation messages are the exact UI strings where one exists: `Title is required`, `Add a title or an item`,
`Title must be at most 200 characters`, `End must be after start`.
The web app maps `PROVIDER_UNAVAILABLE` / network failure to `Could not save: Google Calendar is unavailable` and
`PRECONDITION_FAILED` to `This event was changed elsewhere. Reload it and try again.`

## Types

```ts
type LocalDate = string;   // 'YYYY-MM-DD'
type LocalTime = string;   // 'HH:mm', 00:00–23:59
type DateTime  = string;   // RFC 3339 with offset

interface Calendar {
  id: string;              // 'primary' | 'work' in the mock
  name: string;            // 'Personal' | 'Work' in the mock
  color: string;           // '#rrggbb'
  primary: boolean;
  writable: boolean;
}

interface CalendarEvent {
  kind: 'event';
  id: string;
  calendarId: string;
  title: string;           // 1–200 chars after trim
  description: string;     // '' if none, max 8000
  location: string;        // '' if none, max 500
  allDay: boolean;
  start: DateTime | LocalDate;  // LocalDate iff allDay
  end: DateTime | LocalDate;    // exclusive; LocalDate iff allDay
  colorId: string | null;  // Google event colorId '1'..'11' override, null = calendar color
  color: string;           // resolved '#rrggbb' (colorId palette or calendar color)
  etag: string;
  updated: DateTime;
}

interface TaskItem {
  id: string;
  title: string;           // 1–200 chars after trim
  done: boolean;
}

interface TaskList {
  kind: 'tasklist';
  id: string;              // the Google event id
  calendarId: string;
  title: string;           // 1–200 chars after trim
  date: LocalDate | null;  // null = undated (ARCHITECTURE "Undated task lists"); then time is null too
  time: LocalTime | null;  // null = no time (all-day Google event)
  items: TaskItem[];       // max 200, in display order
  doneCount: number;
  totalCount: number;
  estimateMinutes: number | null; // 5–720; a timed list lasts this long in Google (default 30 when null)
  recurrence: 'daily' | 'weekly' | 'monthly' | null;  // @optional feature; instances have their own ids and ticks
  categoryId: string | null;   // null = no category; unknown/deleted ids are returned as null
  tags: string[];              // max 10, each 1–30 chars, no commas, unique case-insensitively, order kept
  color: string;               // category color, else calendar color
  completedOn: LocalDate | null; // read-only: app-clock date of the write that ticked the last open item; null while
                                 // an item is open (also for lists completed in the Google app); ignored on input
  canvas: { x: number; y: number } | null;  // place on the Canvas in canvas units (integers 0-10000); null = Unsorted
  etag: string;
  updated: DateTime;
}

type CalendarItem = CalendarEvent | TaskList;

interface Category {
  id: string;              // defaults: 'shopping' | 'todo' | 'work' | 'home'; new: 8-char nanoid
  name: string;            // 1–40 chars after trim, unique case-insensitively
  color: string;           // '#rrggbb' lowercase
  icon: string | null;     // one emoji (≤ 8 UTF-16 units) or null
  googleColorId: string;   // derived: nearest Google event color (see "Colors")
}

type ThemeMode = 'system' | 'light' | 'dark';
type ViewName = 'month' | 'week' | 'day';

interface Settings {
  themeMode: ThemeMode;              // default 'system'
  seedColor: string;                 // '#rrggbb', default '#1a73e8'
  defaultView: ViewName;             // default 'month'
  defaultEventColorId: string | null; // Google colorId '1'..'11' or null (= calendar color), default null
  animationLevel: 'full' | 'reduced' | 'off';    // default 'full'; the system "reduce motion" caps it at 'reduced'
  ignoreSystemMotion: boolean;                  // default false; true lets animationLevel apply although the device asks for less motion
  sounds: boolean;                    // default false
  calmMode: boolean;                  // default false
  transitionWarningMinutes: 0 | 5 | 10 | 15;     // default 10; 0 = off
  streakFlame: boolean;               // default true: show the streak flame
  plant: boolean;                     // default true: show the plant widget in the top bar (independent of the scene)
  sunflowers: 'grow' | 'full';        // default 'grow': how many flowers the Sunflower field scene shows
  categories: Category[];            // display order
  updated: DateTime;
  version: number;                   // increments on every change
}
```

### Colors

Google event palette (`colorId` → hex, name): `1` #7986cb Lavender, `2` #33b679 Sage, `3` #8e24aa Grape,
`4` #e67c73 Flamingo, `5` #f6bf26 Banana, `6` #f4511e Tangerine, `7` #039be5 Peacock, `8` #616161 Graphite,
`9` #3f51b5 Blueberry, `10` #0b8043 Basil, `11` #d50000 Tomato.
**Nearest color** = smallest CIE76 ΔE (sRGB → XYZ D65 → CIELAB) to the palette; ties → lower id. Shared pure function
used by server (Google mapping) and web (none needed in UI, but available).
Seed presets: Blue #1a73e8, Purple #6750a4, Teal #006a6a, Green #386a20, Orange #e8710a, Red #b3261e, Pink #c2185b,
Slate #4f6170, Mordor #c43e00 (preset id `mordor`).
Selecting the Mordor preset in the UI also sets `themeMode: 'dark'` and the scene "Mordor" (a theme preference, see
ARCHITECTURE "Themes"). The server only stores the values, and the user can change each one afterwards.
**Scenes** (owner 2026-10-13): the top app bar background is not a setting any more. There is one "Scene" choice
(Spring, Easter, Summer, Summer holidays, Fall, Halloween, Christmas, New Year's Eve, New Year, Winter, Sunflower field, Mordor, None; values `spring`, `easter`, `summer`, `summerholidays`, `fall`, `halloween`, `christmas`, `newyearseve`, `newyear`, `winter`, `sunflowers`, `mordor`, `none`), stored as the `scene` attribute of the person's theme
(`GET/PATCH /api/prefs/theme`, ARCHITECTURE "Themes"; `seasonal` is `off`, `header` or `all`, see there). `PATCH /api/settings` rejects a `scene` field and
`GET /api/settings` no longer returns one. Every scene shows whenever it is chosen: the Sunflower field no longer
depends on any plant setting; the plant widget and the flame are widgets that show per `plant` / `streakFlame`.
**Garden style is gone** (owner 2026-10-13): `Settings.garden` was removed, `PATCH /api/settings` rejects a `garden`
field (400 `VALIDATION_ERROR`), and `plant` (switch) and `sunflowers` (grow / full) replaced it.
*Migration of stored settings* (once, when the server loads a `settings.json` that has `garden` and no `plant`):
`plant = (garden === 'plant')`; the old `garden` key stays in the file (not served) so each person's theme can still
absorb it. When a person's theme is first served after the change (marker `gardenMigrated` in the stored theme):
for `garden === 'sunflowers'` and a Default or Neon preset without a scene override, the override becomes
`sunflowers` (the field they saw); for `plant` or `off`, an override `sunflowers` becomes `none` (they did not see
the field). Other presets and overrides stay as they were. The Default and Neon presets start with scene `none`.
**Prefs** (`GET/PATCH /api/prefs`): besides the Labs switches, `approachingCard`, `approachBar`, `approachWindowHours`,
`tasksCalendarVisible`, `supportCat` and `versionInCorner`, the person pref `leftHanded` (boolean, default `false`; a
non-boolean is a 400) turns on the mirrored phone and touch-tablet layout (ARCHITECTURE "Left-handed mode").
Default categories: `shopping` Shopping #0b8043 🛒, `todo` To-do #3f51b5 ✅, `work` Work #8e24aa 💼,
`home` Home #f4511e 🏠.

## Endpoints

### `GET /api/prefs` → 200, `PATCH /api/prefs` → 200

Per-person preferences (not the shared `Settings`): `labs`, `approachBar`, `approachingCard`, `approachWindowHours`,
`tasksCalendarVisible`, `supportCat`, `versionInCorner` and, since the i18n slice, `language`:
`'auto' | 'en' | 'de' | 'de-x-mainfr' | 'de-x-coldmirror'`, default `'auto'` (follow the device language, ARCHITECTURE
"i18n"). `PATCH` takes any subset, validates all fields first and answers 400 `VALIDATION_ERROR` (field `language`)
for an unknown value; it returns the full preferences.

**Bedtime** (`prefs.bedtime`, per person, ARCHITECTURE "Bedtime mode"): an object
`{ enabled: boolean; mode: 'fixed' | 'dynamic'; bedtime: 'HH:MM'; wake: 'HH:MM'; weekendDifferent: boolean;
weekendBedtime: 'HH:MM'; weekendWake: 'HH:MM'; sleepMinutes: 1..960; leadMinutes: 0..480; reminderMinutes: 0..240 }`,
default `{ enabled: false, mode: 'fixed', bedtime: '23:00', wake: '07:00', weekendDifferent: false, weekendBedtime:
'00:00', weekendWake: '09:00', sleepMinutes: 480, leadMinutes: 60, reminderMinutes: 30 }`. `PATCH` takes any subset of
its fields (merged into the stored object); a wrong type, time or range is a 400 `VALIDATION_ERROR` (field `bedtime`).

### `GET /api/health` → 200

```ts
{ status: 'ok'; provider: 'mock' | 'google'; providerStatus: 'ok' | 'unavailable';
  version: string; time: DateTime; testMode: boolean }
```
Always 200 while the server runs. `providerStatus` comes from a cheap provider ping (cached ≤ 10 s; not cached while an
outage is simulated).

### `GET /api/config` → 200

```ts
{
  now: string;              // ISO UTC (toISOString), honours the test clock
  clockFrozen: boolean;     // true while a test clock is set
  timeZone: string;         // 'Europe/Berlin'
  weekStartsOn: 1;          // Monday
  pollIntervalMs: number;   // POLL_INTERVAL_MS env (default 30000), test override; 0 = polling disabled
  provider: 'mock' | 'google';
  testMode: boolean;
  publicUrl: string | null; // PUBLIC_URL env
  version: string;
}
```

**How the web app derives "today"**: on startup (and on every focus/visibility sync) it fetches `/api/config`.
If `clockFrozen` the app's clock is the constant `now`. Otherwise it stores `offset = Date.parse(now) - Date.now()` at
fetch time and uses `Date.now() + offset`. "Today" is the date of that instant in `timeZone`. If `/api/config` fails
(offline), the app uses the device clock, `Europe/Berlin`, Monday, 30 s polling. All date logic in `web/` goes through
one `useClock()` composable; nothing else calls `new Date()` for "now".

### `GET /api/calendars` → 200

`{ calendars: Calendar[] }` — every calendar in the person's Google list (own and shared), each with
`hidden: boolean` (the person's choice). Errors: 503.

### `PATCH /api/calendars/:id` → 200

Body `{ hidden: boolean }`; stores the person's choice and returns the updated `Calendar`. 404 for an unknown id.

### `GET /api/items?from=YYYY-MM-DD&to=YYYY-MM-DD[&calendarIds=a,b]` → 200

Returns every event and task list overlapping `[from 00:00, to 00:00)` local time (`to` exclusive), from all calendars
(or the listed ones).

```ts
{ items: CalendarItem[]; from: LocalDate; to: LocalDate; syncedAt: DateTime }
```
Sorted by start (all-day first per day, then by time, then title). A Google event whose
`extendedProperties.private.kind === 'tasklist'` is returned as `TaskList`, all others as `CalendarEvent`. Cancelled
events are omitted. Errors: 400 (`from`/`to` invalid, `to <= from`, range > 100 days), 503, 502.

Optional `&also=YYYY-MM-DD..YYYY-MM-DD` (one extra range, same rules) adds that range's items to the same response, so
the client's poll stays one request when it also keeps today loaded for the Approaching card (owner, 2026-10-13;
alternatives weighed: two requests per poll — breaks the polling budget; refreshing today less often — staler card).
The response then also carries `also: { from, to }`; items present in both ranges appear once.

### Events

| Method | Path | Body | Success |
|---|---|---|---|
| `POST` | `/api/events` | `CreateEventInput` | `201` `CalendarEvent` |
| `GET` | `/api/events/:id` | – | `200` `CalendarEvent` |
| `PATCH` | `/api/events/:id` | `UpdateEventInput` | `200` `CalendarEvent` |
| `DELETE` | `/api/events/:id` | – | `204` |

```ts
interface CreateEventInput {
  calendarId?: string;     // default: primary calendar
  title: string;
  description?: string;
  location?: string;
  allDay: boolean;
  start: DateTime | LocalDate;
  end: DateTime | LocalDate;   // must be > start (all-day: exclusive date > start date)
  colorId?: string | null;
}
type UpdateEventInput = Partial<CreateEventInput>;  // calendarId change = move to another calendar
```
Validation: title required/trimmed/≤200; `allDay` true ⇒ both `LocalDate`, false ⇒ both `DateTime`; `end > start`;
duration ≤ 366 days. `PATCH` validates the merged result. Errors: 400, 404 (unknown id, or id is a task list), 412,
502, 503. Events cannot be turned into task lists or vice versa.

| `DELETE` | `/api/tasklists/:id` | – | `204` |

| `PATCH` | `/api/tasklists/:id/items/:itemId` | `{ title?: string; done?: boolean }` | `200` `TaskList` |
| `DELETE` | `/api/tasklists/:id/items/:itemId` | – | `200` `TaskList` |

```ts
interface CreateTaskListInput {
  // no calendarId: task lists always go to the person's tasks calendar (ARCHITECTURE §3)
  title: string;          // may be empty/blank (stored as "") when at least one non-blank item is given
  date: LocalDate | null; // required key; null creates an undated list (no time, no recurrence)
  time?: LocalTime | null;
  items?: { title: string; done?: boolean }[];   // blank titles are dropped
  categoryId?: string | null;   // must exist in settings, else 400
  tags?: string[];
  estimateMinutes?: number | null;
  recurrence?: 'daily' | 'weekly' | 'monthly' | null;
}
interface UpdateTaskListInput {
  title?: string;
  date?: LocalDate | null; // a date makes the list appear in the calendar; null makes it undated (drops the time)
  time?: LocalTime | null; // null removes the time
  items?: { id?: string; title: string; done: boolean }[];  // full replacement (used by fixtures)
  categoryId?: string | null;
  tags?: string[];
  estimateMinutes?: number | null;
  canvas?: { x: number; y: number } | null; // x, y integers 0-10000 (else 400, field `canvas`); null clears the place
}
```
Item ops return the whole updated `TaskList`. `index` inserts at a position (default: append). `itemIds` must be a
permutation of the current ids, else 400. A list with an empty title and no items left → 400 `Add a title or an item`. Blank item titles → 400 (the UI ignores blank input without calling the API).
Errors: 400, 404 (unknown list or item, or id is a plain event), 412 (`PATCH`/`DELETE` of the list with stale
`If-Match`), 502, 503.

### Settings and categories

Stored server-side in `DATA_DIR/settings.json` (single user, independent of the provider; atomic writes). Created with
the defaults on first start.

| Method | Path | Body | Success |
|---|---|---|---|
| `GET` | `/api/settings` | – | `200` `Settings` |
| `PATCH` | `/api/settings` | `Partial<Omit<Settings, 'categories' \| 'updated' \| 'version'>>` | `200` `Settings` |
| `POST` | `/api/categories` | `{ name: string; color: string; icon?: string \| null }` | `201` `Settings` |
| `PATCH` | `/api/categories/:id` | `{ name?; color?; icon? }` | `200` `Settings` |
| `DELETE` | `/api/categories/:id` | – | `200` `Settings` |
| `PUT` | `/api/categories/order` | `{ categoryIds: string[] }` | `200` `Settings` |

Validation messages: `Name is required`, `A category with this name already exists`, `Enter a color like #1a73e8`
(invalid hex, also for `seedColor`). Colors are normalised to lowercase. `PATCH /api/settings` accepts
`If-Match: <version>` (412 if stale); the web app sends it. Deleting a category does not rewrite Google events: task
lists keep the stale `categoryId` in Google, and the API reports them as `categoryId: null` (calendar color). The
settings endpoints do not touch the provider, so they work during a Google outage.

Filtering by category/tag is done in the web app on the loaded items (no server query parameters). Filter state lives
in the URL query: `categories=<id>[,<id>…]` (`none` = without category) and `tags=<tag>[,<tag>…]`, e.g.
`/week/2026-10-12?categories=shopping,none&tags=weekend`. Categories are OR-ed, tags are OR-ed, and the two groups are
AND-ed. Events are never filtered.

`PATCH /api/prefs/theme` `overrides` also takes the fine-tuning fields (ARCHITECTURE "Fine-tuning sliders, density and icon choices"): `glowStrength` (integer 0..150), `radius` (integer 0..28), `tint` (integer 5..60), `density` (`compact|comfortable|airy`), `checkbox` (`round|square|rounded`), `checkFill` (`filled|outline`), `check` (`tick|bold|cross|dot`), `icons` (`outlined|rounded|sharp`). Out-of-range or unknown values answer `400`. The same optional fields exist in `calendar-theme/2`.

### Imported themes (`/api/themes`)

Per person (their own Google account when sign-in is on), stored in `DATA_DIR/users/<sub>/themes/` (ARCHITECTURE
"Theme engine and AI themes"). A theme is a `calendar-theme/2` document (`shared/theme.schema.json`, no SVG in it) plus
an optional own top bar picture kept next to it.

```ts
type Picture = { light?: string; dark?: string };   // SVG text, each ≤ 100 KB, at least one
```
- `GET /api/themes` → `200` `{ themes: { id: string; doc: ThemeDoc; picture?: Picture }[] }`, oldest first.
- `POST /api/themes` with `{ theme: ThemeDoc; picture?: Picture }` → `201` `{ id; doc; picture?; sanitized: boolean }`.
  The server validates the document and the picture and sanitises the picture's SVG again (what is stored is the
  sanitised picture); `sanitized` is true when something unsafe was removed. `400 VALIDATION_ERROR` with the first
  problem as `message` and every problem in `details[].issue`, in plain words (`glow must be one of off, soft, neon`;
  `picture.light must be an SVG picture (starting with <svg)`). Also `400` when the person already has 20 themes
  (`You can keep at most 20 themes. Delete one first.`).
- `DELETE /api/themes/:id` → `204`; `404` for an unknown id.

A person chooses an imported theme with `PATCH /api/prefs/theme` `{ preset: "theme:<id>" }` (a preset name or `theme:<id>`).
`GET/PATCH /api/prefs` has the Labs switch `labsOwnThemes: boolean` (default `false`) for showing the AI prompt and
the import in the theme menu; it does not affect themes, which the server stores and lists regardless. `POST /api/__test/reset` forgets
every person's imported themes.

### Summary (year view, month picker dots)

`GET /api/summary?from=YYYY-MM-DD&to=YYYY-MM-DD` (to exclusive, max 400 days) → `200`
```ts
{ days: Record<LocalDate, { events: number; tasklists: number; openTasklists: number; density: 0 | 1 | 2 | 3 }> }
```
Only days with at least one item are listed. Multi-day items count on every covered day. Density: 0 items → 0,
1 → 1, 2–3 → 2, ≥ 4 → 3. Errors: 400, 502, 503.

### Open task lists (tray, carry-over)

`GET /api/tasklists/open?today=YYYY-MM-DD&days=30` → `200 { items: TaskList[]; finishedToday: TaskList[] }`. `items`:
task lists with at least one unticked item dated in `[today − days, today]` (inclusive). `finishedToday`: task lists
in the same date window with `completedOn = today` (finished today, shown struck through in the tray). Order of both:
date ascending, then untimed before timed, then time, then title. The web app shows lists dated before `today` as **carried over** on today (and not on their own
date); lists with no open items are never carried. `days` max 90, default 30.

### All open task lists (Tasks view)

`GET /api/tasklists/all-open?today=YYYY-MM-DD` → `200 { items: TaskList[] }`: every task list that is not complete
(a list without items counts as open), undated lists and lists dated in `[today − 365, today + 365]`. Unordered; the
web app groups and sorts. Errors: 400, 502, 503. Undated lists are returned only here and by `GET /api/tasklists/:id`;
`/api/items`, `/api/summary` and `/api/tasklists/open` never return them.

### Archived task lists (Tasks view, Archive tab)

`GET /api/tasklists/archive?today=YYYY-MM-DD` → `200 { items: TaskList[] }`: every finished task list (at least one
item, all ticked), dated or undated: the lists carrying the private marker `done=1` of any age, plus the finished
lists dated in `[today − 365, today + 365]` (lists written before the marker existed). Unordered; the web app sorts
(newest `completedOn` first, lists without `completedOn` last by date). Errors: 400, 502, 503. `all-open` never returns
finished lists; the date-range endpoints are unchanged.

### Prefs: Tasks view

`GET/PATCH /api/prefs` also carry `tasksGroupBy: 'time' | 'category' | 'none'` (default `time`) and
`tasksSortBy: 'date' | 'name' | 'category' | 'changed' | 'progress'` (default `date`); `tasksSortDir: 'default' | 'reversed'` (default `default`, relative to the sort key's own direction); any other value is `400`. `tasksFilter: { categories: string[]; when: 'all' | 'nodate' | 'dated' | 'overdue' | 'today' | 'tomorrow' | 'week' }` (default `{ categories: [], when: 'all' }`) is the Tasks view's filter (ARCHITECTURE "Tasks filter"); `categories` holds at most 50 unique strings of 1-64 characters (category ids, or `none`), the whole object is replaced by a `PATCH`, any other shape or value is `400` (field `tasksFilter`). `undatedDone: 'calendar' | 'archive'` (default `calendar`) decides what finishing an undated list does (ARCHITECTURE "Archive"); any other value is `400`.

### Canvas (`/api/canvas`)

The person's **areas** on the Tasks view's Canvas (ARCHITECTURE "Canvas"), one JSON document per person in
`DATA_DIR/users/<sub>/canvas.json`; not in Google. The place of a note is not here: it is the `canvas` field of the
task list.

| Method | Path | Body | Success |
|---|---|---|---|
| `GET` | `/api/canvas` | – | `200` `CanvasDoc` (`{ version: 1, areas: [] }` for a person without one) |
| `PUT` | `/api/canvas` | `{ areas: CanvasArea[] }` | `200` `CanvasDoc` (replaces the whole document) |

```ts
interface CanvasArea {
  id: string;      // 1-32 characters of A-Za-z0-9_-, unique in the document; the client makes it
  name: string;    // trimmed, 1-60 characters
  color: string;   // #rrggbb
  x: number; y: number;   // top-left corner in canvas units, integers 0-10000
  w: number; h: number;   // size, integers 160-4000 wide, 120-4000 high
}
interface CanvasDoc { version: 1; areas: CanvasArea[] }   // at most 50 areas
```
A `PUT` with an unknown field, a bad value, a duplicate id or more than 50 areas is `400 VALIDATION_ERROR` and changes
nothing. Last write wins (no etag). The document is per person (the signed-in person; one shared document with sign-in
off). `POST /api/__test/reset` forgets every person's document.

### Motivation: check-in streak and plant

Stored server-side in `DATA_DIR/motivation.json` (single user, synced across devices). Dates are local dates of the
app clock (`TZ`).

```ts
interface Motivation {
  streak: { current: number; best: number; lastCheckIn: LocalDate | null; checkedInToday: boolean };
  plant: {
    growth: number;            // total points, never decreases
    stage: 'Seed' | 'Sprout' | 'Small plant' | 'Leafy' | 'Flowering';
    stageIndex: 0 | 1 | 2 | 3 | 4;
    nextStageAt: number | null;
    todayPoints: number;       // points earned today (0–30)
    lastWatered: LocalDate | null;
    flowers: number;           // sunflower count, 0–30
    vitality: 100 | 75 | 50 | 25;
    mood: 'happy' | 'thirsty' | 'dry' | 'droopy';
    message: string;
  };
}
```

| Method | Path | Success |
|---|---|---|
| `GET` | `/api/motivation` | `200` `Motivation` |
| `POST` | `/api/streak/checkin` | `200 { current, best, checkedInToday: true, newToday: boolean, motivation: Motivation }` |

**Streak rules:** the web app calls `POST /api/streak/checkin` once after startup and again when the app becomes
visible on a new local day. If the last check-in was yesterday, `current + 1`; if it was today, unchanged
(`newToday: false`); otherwise `current = 1` (quiet reset). `best = max(best, current)`. Idempotent per day.

**Plant rules** (all server-side, so they cannot be spammed from a client):

| Action | Points | Counted when |
|---|---|---|
| Daily check-in | +10 | first check-in of the day |
| Create event | +5 | `POST /api/events` returns 201 |
| Create task list | +5 | `POST /api/tasklists` returns 201 |
| Tick an item | +2 | an item goes from not done to done; each item id counts at most once per day |

- Daily cap: 30 points (`todayPoints` resets at local midnight). Points above the cap are dropped.
- Stage thresholds on `growth`: Seed 0, Sprout 20, Small plant 60, Leafy 140, Flowering 280.
- Watering sets `lastWatered = today` (any awarded point, even if capped to 0 extra points).
- Mood from `d` = calendar days since `lastWatered`: d ≤ 1 → happy (100); 2 → thirsty (75); 3 → dry (50);
  ≥ 4 → droopy (25, the floor). No `lastWatered` → happy. Growth never decreases; the plant never dies.
- Messages (exact): happy "Your plant is happy", thirsty "Your plant is a little thirsty", dry "Your plant could use
  some water", droopy "Your plant is resting. Anything you do will perk it up."
- Streak and plant points are recorded regardless of `streakFlame` / `plant` (these settings only change what is shown).
- **Sunflower field** (the scene of that name) uses the same points and mood: `plant.flowers = min(30,
  floor(growth / 40))`. Flowers never decrease. With `Settings.sunflowers = 'grow'` the field shows `plant.flowers`;
  with `'full'` it shows a fixed 30 and never grows (no `bloom`). The UI shows at most 15 on viewports < 600 px wide
  and up to 30 above that; the accessible label always states the count of the mode ("Sunflower field: 5 flowers",
  singular "1 flower", "Sunflower field: 30 flowers" for the full field). In `grow` mode a newly earned flower (the
  count went up since the last `Motivation` the client saw) plays the `bloom` effect.
- Server-side awarding hooks: the event/task list/item handlers call `MotivationService.award(kind, key)`. Mutation
  responses carry the header `X-Motivation-Changed: 1` when points were awarded, and the web app then refetches
  `/api/motivation`.

### Diagnostics (`POST /api/diag/sync-error`) → 204

The web app sends this once when it enters the "Can't reach Google Calendar" state. The server only logs it
(`client_sync_error`, ARCHITECTURE "Diagnostics"); nothing is stored and the response has no body. Needs a session while
sign-in is on. Body (at most 1 KiB, unknown fields → 400):

```ts
interface SyncErrorBeacon {
  kind: 'network' | 'timeout' | 'http' | 'abort';
  status?: number;       // 100-599, the HTTP status for kind "http"
  task: string;          // which refresher failed: items, summary, settings, calendars, a registered task, or "other"; 1-32 of A-Z a-z 0-9 _ . : -
  online: boolean;       // navigator.onLine
  resumed: boolean;      // the page became visible less than 5 s before the failure
  app: boolean;          // Android app (true) or browser (false)
  ageSec?: number;       // 0-604800, set when the beacon could not be sent at once and went out after the next good sync
}
```

At most one beacon per client (session) per minute: a second one → `429 RATE_LIMITED`. The web app ignores every
failure of this call.

## Static files

Everything outside `/api` is the built web app. Unknown non-file paths (e.g. `/week/2026-10-12`) return `index.html`
(SPA fallback, `Cache-Control: no-cache`). Hashed assets under `/assets/` get `Cache-Control: public, max-age=31536000,
immutable`. `/manifest.webmanifest` (`application/manifest+json`), `/sw.js` (`no-cache`), and icons under `/icons/` are
served from the build output. Text responses (HTML, JS, CSS, JSON, manifest) are served compressed (brotli or gzip,
pre-compressed at build time where possible) when the client accepts it.

### `GET /app.apk` (Android app download)

Serves `DATA_DIR/downloads/app.apk` if the file exists: `200`, `Content-Type: application/vnd.android.package-archive`,
`Content-Length`, `Content-Disposition: attachment; filename="calendar.apk"`, `Cache-Control: no-cache`. Without the file
`404` with the usual JSON error body (never the SPA `index.html`). Public (outside `/api`, no session needed: the
file holds no secrets). The file is put there by `scripts/android-build.sh`, not by the server.

## Sign-in (auth on when `PROVIDER=google`; off with `PROVIDER=mock` unless a test turns it on)

| Method | Path | Effect |
|---|---|---|
| `GET` | `/api/auth/google/start` | 302 to Google consent: scopes `openid email` + calendar, `access_type=offline`, `prompt=consent`, a `state` bound to a short-lived cookie. |
| `GET` | `/api/auth/google/callback?code&state` | Exchanges the code. The `id_token` email must be in `ALLOWED_EMAILS` (case-insensitive): then the refresh token is stored for that person, a session is created (cookie `cal_session`) and the response is 302 to `/`; otherwise no token is kept and the response is 302 to `/signin?error=private`. 400 on invalid `state`. |
| `GET` | `/api/auth/google/start` (while signed in) | Works with an existing session too (re-grant); the URL carries `include_granted_scopes=true`, so a newly granted scope adds to the old ones. |
| `GET` | `/api/auth/google/start?app=1` | The Android app's flow (Google refuses OAuth in a WebView, so the app opens this URL in the system browser). Same as without `app`, but the `state` remembers the flag. On a successful callback the response is **200 HTML** (no `cal_session` cookie, `Cache-Control: no-store`) that opens the deep link `lan.mordor.calendar://auth?code=<code>` (by script, plus a visible link `#open-app` for browsers that refuse a script launch). `<code>` is random (128 bit), single-use, valid 60 s and bound to the session just created; a not-allowed address still ends in 302 `/signin?error=private` with no code. Only `app=1` selects this; the browser flow is unchanged. |
| `GET` | `/api/auth/app-exchange?code` | Public. The app's WebView loads it from the deep link: a valid code sets the normal `cal_session` cookie and answers 302 to `/` (`/?calendar=missing` when the calendar scope is missing). An unknown, used or expired code, or none, answers **400** with a small HTML page ("This sign-in link has expired or was already used", link to `/signin`) and sets no cookie. `Cache-Control: no-store`. Codes are kept in memory only (a restart invalidates them). |
| `GET` | `/api/auth/me` | `{ email, name }` of the signed-in person; 401 without a session; `{ email: null, name: null }` while auth is off (so the client can tell "off" from "signed out"). Public. |
| `POST` | `/api/auth/signout` | Ends the session (server side) and clears the cookie; 204. |

While auth is on, every other `/api/*` route except `/api/health`, the two OAuth routes and `/api/auth/app-exchange` answers **401
`UNAUTHENTICATED`** without a valid session. When a person's Google refresh fails with `invalid_grant`, the API answers
**401 `GOOGLE_REAUTH`** for that person; the client then shows "sign in with Google again". When the person did not
tick Google's calendar checkbox (granular consent), the callback reads the granted `scope` from the token response
(authoritative; the `scope` query parameter is only a hint), stores it in `google-token.json` next to the refresh token,
signs the person in and redirects to `/?calendar=missing`; calendar calls then answer **403
`CALENDAR_PERMISSION_MISSING`** (stored scope lacks calendar, or Google answers 403 `insufficientPermissions` /
`ACCESS_TOKEN_SCOPE_INSUFFICIENT`, also for tokens stored before the scope was recorded). The client then shows
"grant calendar access". After sign-in and sign-out the server drops that person's cached provider so a new token
applies without a restart. Redirect URI =
`GOOGLE_REDIRECT_URI` (default `${PUBLIC_URL}/api/auth/google/callback`).
