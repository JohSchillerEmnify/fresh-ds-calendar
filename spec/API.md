# REST API contract

Served by `server/` (Fastify) under `/api`, consumed by `web/`. JSON only (`Content-Type: application/json; charset=utf-8`).
Types below are normative; the server validates requests with equivalent JSON schemas (Fastify `schema`), and the
TypeScript types live in one shared module (`server/src/api/types.ts`, copied or path-aliased into `web/`).

## Conventions

- **Time zone**: `TZ` env (default `Europe/Berlin`). All "date-only" values are local dates in that zone.
- **Timed values**: RFC 3339 with offset, e.g. `"2026-10-14T09:00:00+02:00"`. Server responses always use the
  calendar time zone offset. Requests may use any offset or `Z`.
- **All-day values**: `"YYYY-MM-DD"`. `end` is **exclusive** (Google semantics): a one-day event on 2026-10-16 has
  `start: "2026-10-16"`, `end: "2026-10-17"`. The UI shows inclusive end dates.
- **IDs**: opaque strings from the provider (Google event ids: `[a-v0-9]{5,1024}`). Task list item ids: 8-char
  `[A-Za-z0-9_-]` (nanoid) generated by the server.
- **Concurrency**: every item has an `etag`. `PATCH`/`DELETE` on events and task lists accept an optional
  `If-Match: <etag>` header. If present and stale → `412 PRECONDITION_FAILED`. The web app always sends it for event
  edits/deletes and task list detail edits. Item-level operations (`/items/...`) do **not** require it: the server
  re-reads the latest task list, applies the operation, and writes back with the fresh etag (retrying up to 3 times on
  a provider-side 412), so concurrent ticks from Google and the app merge.
- **Unknown fields** in request bodies → `400 VALIDATION_ERROR`.
- **Idempotency (ADR 0031)**: every write (`POST`, `PATCH`, `DELETE`, item operations) may carry `Idempotency-Key: <opaque,
  at most 64 characters>`, made by the app per outbox entry. The server keeps the answer of a key for 24 hours per
  person (in the person's `idempotency.json`, so a server restart does not forget it); a resend with the same key answers the first result (status and body) and changes nothing again. Only successful answers are kept. A key reused
  for a different method or path → `422 IDEMPOTENCY_KEY_REUSED`. Without the header a write behaves as before.

## Error format

Every non-2xx response:

```ts
interface ApiError {
  error: {
    code: ErrorCode;
    message: string;              // English, may be shown to the user
    key?: string;                 // message key (web catalogue path), set for user-facing validation errors
    details?: { field?: string; issue?: string }[];
  };
}
type ErrorCode =
  | 'VALIDATION_ERROR'      // 400
  | 'NOT_FOUND'             // 404 (also unknown /api routes and /api/__test/* when TEST_MODE is off)
  | 'FORBIDDEN'             // 403 a member of a shared list tried an owner-only action; a non-GET request from an origin that is not allowed
  | 'PAYLOAD_TOO_LARGE'     // 413 a body over 256 KB (themes 400 KB)
  | 'UNSUPPORTED_MEDIA_TYPE' // 415 a body that is not `application/json`
  | 'PRECONDITION_FAILED'   // 412 etag mismatch
  | 'CONFLICT'              // 409 the data needs a person's decision first (a repeating list shown twice on a date)
  | 'PROVIDER_ERROR'        // 502 provider returned an unexpected error
  | 'PROVIDER_UNAVAILABLE'  // 503 provider unreachable / outage / auth failure
  | 'RATE_LIMITED'          // 503 Google's per-person rate limit is in force and nothing cached can answer (`Retry-After`); 429 `POST /api/diag/sync-error`
  | 'INTERNAL';             // 500
```

`key`, when present, names a message of the web catalogue (for example `errors.validation.endAfterStart`); the web
app shows that message in the person's language and falls back to the English `message` for unknown keys.
Validation messages are the exact UI strings where one exists: `Title is required`, `Add a title or an item`,
`Title must be at most 200 characters`, `End must be after start`.
`RATE_LIMITED` with status 503 carries `Retry-After: <seconds>` (the rest of the server's cooldown, or Google's own
`Retry-After` when it sent one). The web app does not retry before then and shows no banner while it has data (see
"Stale data").
The web app maps `PROVIDER_UNAVAILABLE` / network failure to `Could not save: Google Calendar is unavailable` and
`PRECONDITION_FAILED` to `This event was changed elsewhere. Reload it and try again.`

## Types

```ts
type LocalDate = string;   // 'YYYY-MM-DD'
type LocalTime = string;   // 'HH:mm', 00:00–23:59
type DateTime  = string;   // RFC 3339 with offset

interface Calendar {
  id: string;              // 'primary' | 'work' in the mock
  name: string;            // 'Personal' | 'Work' in the mock
  color: string;           // '#rrggbb'
  primary: boolean;
  holiday?: true;          // a Google holiday calendar (id ends in '#holiday@group.v.calendar.google.com'): listed under Settings › Calendars › Holidays
  writable: boolean;       // Google role owner or writer, whoever owns the calendar: editing follows Google's permissions; events are created and moved only into these (see CalendarEvent.readOnly)
  contactsPermission?: 'granted' | 'missing';  // only on the virtual `birthdays`: the person's token has `contacts.readonly` (contact birthdays are read) or not (feature contact-birthdays)
}

interface CalendarEvent {
  kind: 'event';
  id: string;
  calendarId: string;
  title: string;           // 1–200 chars after trim
  description: string;     // '' if none, max 8000
  location: string;        // '' if none, max 500
  place?: Place;           // the place picked for the location (feature event-location); absent for typed text, and once `location` is neither `place.name` nor starts with `"<place.name>, "` (changed elsewhere)
  allDay: boolean;
  start: DateTime | LocalDate;  // LocalDate iff allDay
  end: DateTime | LocalDate;    // exclusive; LocalDate iff allDay
  colorId: string | null;  // Google event colorId '1'..'11' override, null = calendar color
  color: string;           // resolved '#rrggbb' (colorId palette or calendar color; always the calendar color for an event of the contacts Birthdays calendar)
  special?: 'birthday' | 'anniversary';  // only on Google birthday entries: `eventType` 'birthday' or an event of the contacts "Birthdays" calendar; 'anniversary' when `birthdayProperties.type` is 'anniversary', else 'birthday'
  readOnly?: true;         // not in a writable calendar (Google role reader or freeBusyReader; reason `calendar`, "Calendar of …"), or an invitation (someone else organises it, guests may not edit); PATCH/DELETE answer 403 `calendar.event.notOwn`. Birthdays: the contacts Birthdays calendar, or a calendar that is not writable; PATCH/DELETE answer 400
  readOnlyReason?: { kind: 'invitation' | 'calendar'; by: string } | { kind: 'contact' };  // with readOnly: "Invitation from <by>" / "Calendar of <by>"; `contact`: a birthday from Google Contacts (the app shows "Change this birthday in Google Contacts"); absent for the contacts Birthdays calendar
  contactBirthday?: { resourceName: string; birthYear?: number };  // only on a date read from Google Contacts (ADR 0043): the People API resource name (`people/c123`); `birthYear` only when the contact has a year (the app shows "Turns N", N = year of the shown day - birthYear), never for a birthday without a year
  dateLocked?: true;       // birthdays only: linked to a contact or `birthdayProperties.type` 'self'; Google keeps the date (name and colour stay editable)
  etag: string;
  updated: DateTime;
}

interface TaskItem {
  id: string;
  title: string;           // 1–200 chars after trim
  done: boolean;
}

interface TaskList {
  kind: 'tasklist';
  id: string;              // the Google event id
  calendarId: string;
  title: string;           // 1–200 chars after trim
  date: LocalDate | null;  // null = undated (ADR 0017); then time is null too
  time: LocalTime | null;  // null = no time (all-day Google event)
  items: TaskItem[];       // max 200, in display order
  doneCount: number;
  totalCount: number;
  estimateMinutes: number | null; // 5–720; a timed list lasts this long in Google (default 30 when null)
  recurrence: 'daily' | 'weekly' | 'monthly' | null;  // @optional feature; instances have their own ids and ticks
  seriesId?: string;      // on an occurrence of a repeating list: the id of its series (Google recurringEventId); absent otherwise
  seriesKey?: string;     // on an occurrence: the same for every part of a list split by a "this and following" change
  categoryId: string | null;   // null = no category; unknown/deleted ids are returned as null
  tags: string[];              // max 10, each 1–30 chars, no commas, unique case-insensitively, order kept
  color: string;               // category color, else calendar color
  completedOn: LocalDate | null; // read-only: app-clock date of the write that ticked the last open item; null while
                                 // an item is open (also for lists completed in the Google app); ignored on input
  createdOn?: LocalDate;       // app-clock day the list was made (create input may send it: an offline create keeps its day); absent on older lists
  canvas: { x: number; y: number } | null;  // place on the Canvas in canvas units (integers 0-10000); null = Unsorted
  etag: string;
  updated: DateTime;
}

type CalendarItem = CalendarEvent | TaskList;

interface Category {
  id: string;              // defaults: 'shopping' | 'todo' | 'work' | 'home'; new: 8-char nanoid
  name: string;            // 1–40 chars after trim, unique case-insensitively
  color: string;           // '#rrggbb' lowercase
  icon: string | null;     // one emoji (≤ 8 UTF-16 units) or null
  googleColorId: string;   // derived: nearest Google event color (see "Colors")
}

type ThemeMode = 'system' | 'light' | 'dark';
type ViewName = 'month' | 'week' | 'day';

interface Settings {
  themeMode: ThemeMode;              // default 'system'
  seedColor: string;                 // '#rrggbb', default '#1a73e8'
  defaultView: ViewName;             // default 'month'
  animationLevel: 'full' | 'reduced' | 'off';    // default 'full'; the system "reduce motion" caps it at 'reduced'
  ignoreSystemMotion: boolean;                  // default false; true lets animationLevel apply although the device asks for less motion
  sounds: boolean;                    // default false
  calmMode: boolean;                  // default false
  sunflowers: 'grow' | 'full';        // default 'grow': how many flowers the Sunflower field scene shows
  categories: Category[];            // display order
  updated: DateTime;
  version: number;                   // increments on every change
}
```

### Colors

Google event palette (`colorId` → hex, name): `1` #7986cb Lavender, `2` #33b679 Sage, `3` #8e24aa Grape,
`4` #e67c73 Flamingo, `5` #f6bf26 Banana, `6` #f4511e Tangerine, `7` #039be5 Peacock, `8` #616161 Graphite,
`9` #3f51b5 Blueberry, `10` #0b8043 Basil, `11` #d50000 Tomato.
**Nearest color** = smallest CIE76 ΔE (sRGB → XYZ D65 → CIELAB) to the palette; ties → lower id. Shared pure function
used by server (Google mapping) and web (none needed in UI, but available).
Seed presets: Blue #1a73e8, Purple #6750a4, Teal #006a6a, Green #386a20, Orange #e8710a, Red #b3261e, Pink #c2185b,
Slate #4f6170, Mordor #c43e00 (preset id `mordor`).
Selecting the Mordor preset in the UI also sets `themeMode: 'dark'` and the scene "Mordor" (a theme preference, see
feature theme-menu). The server only stores the values, and the user can change each one afterwards.
**Scenes** (owner 2026-10-13): the top app bar background is not a setting any more. There is one "Scene" choice
(Spring, Easter, Summer, Summer holidays, Fall, Halloween, Christmas, New Year's Eve, New Year, Winter, Sunflower field, Mordor, None; values `spring`, `easter`, `summer`, `summerholidays`, `fall`, `halloween`, `christmas`, `newyearseve`, `newyear`, `winter`, `sunflowers`, `mordor`, `none`), stored as the `scene` attribute of the person's theme
(`GET/PATCH /api/prefs/theme`, feature theme-menu; `seasonal` is `off`, `header` or `all`, see there). `PATCH /api/settings` rejects a `scene` field and
`GET /api/settings` no longer returns one. Every scene shows whenever it is chosen: the Sunflower field no longer
depends on any plant setting; the plant widget and the flame are widgets that show per the person pref `streak`.
**Garden style is gone** (owner 2026-10-13): `Settings.garden` was removed, `PATCH /api/settings` rejects a `garden`
field (400 `VALIDATION_ERROR`), and `plant` (switch) and `sunflowers` (grow / full) replaced it.
*Migration of stored settings* (once, when the server loads a `settings.json` that has `garden` and no `plant`):
`plant = (garden === 'plant')`; the old `garden` key stays in the file (not served) so each person's theme can still
absorb it. When a person's theme is first served after the change (marker `gardenMigrated` in the stored theme):
for `garden === 'sunflowers'` and a Default or Neon preset without a scene override, the override becomes
`sunflowers` (the field they saw); for `plant` or `off`, an override `sunflowers` becomes `none` (they did not see
the field). Other presets and overrides stay as they were. The Default and Neon presets start with scene `none`.
**Prefs** (`GET/PATCH /api/prefs`): besides the Labs switches, `approachingCard`, `approachBar`, `approachWindowHours`,
`tasksCalendarVisible`, `supportCat` and `versionInCorner`, the person pref `taskCategories` (boolean, default `true`; a non-boolean is a 400; `false` hides every task category UI, the
stored `categoryId`s are untouched), the person pref `leftHanded` (boolean, default `false`; a
non-boolean is a 400) turns on the mirrored phone and touch-tablet layout (feature left-handed-mode), and `showCarriedFrom` (boolean,
default `true`) shows the "From <day>" label on task lists carried over to today.
The person pref `labsViews` (object, default `{}`): per Labs view id (`clock`, `timeline`, `strip`, …) whether the view
switcher offers it; ids match `^[a-z][a-z0-9-]*$` (at most 32, values boolean; anything else is a 400). `PATCH` merges
per id. A missing id follows the client's registry default (Strip off, others on).
The person pref `stableViews` (object, default `{}`) is the same for the main views of the view switcher (`year`,
`month`, `week`, `day`, `tasks`, `clock-rings`; the last is the Clock): per id whether the switcher offers the view.
Same validation (a 400 for anything but ids mapped to booleans) and per-id merge; a missing id is on. The server does
not keep one view on: the client disables the last switch, and when every view is off it offers all of them.
`approachWindowHours` is a whole number from 1 to 24 (default 3; anything else is a 400).
`taskOpen` (`'inline' | 'drawer'`, default `'inline'`) is what a tap on a task list card does: grow it in place or
open the list sheet.
`growSeveral` (boolean, default `true`) lets several task list cards stay grown at once; off, growing a card collapses the one
grown before.
`sendReportsAuto` (boolean, default `false`, never switched on by the app) lets the device send its error and crash log to `POST /api/diag/device-log` by itself (feature device-log).
The person prefs `navPhone` (default `bottom`) and `navDesktop` (default `rail`) place the view switcher (`bottom`, `top` or
`rail`; `navPhone` also accepts `drawer`, the side menu of feature nav-expressive; any other value is a 400; feature nav-position).
The person pref `bottomBarSize` (`'auto' | 'expressive' | 'compact'`, default `'auto'`: Compact on phones, Expressive elsewhere;
anything else is a 400) is the bottom bar's size (feature nav-expressive).
The person pref `headerLayout` (`'auto' | 'two-rows' | 'one-row'`, default `'auto'`: Compact = `one-row` on phones, Expressive =
`two-rows` elsewhere; anything else is a 400) is the top bar's size (features header-layout, header-expressive). It is a person pref, not part of the theme: `PATCH /api/prefs/theme`, theme
files and theme import/export never carry it. `approachTimeLeft` (boolean, default `true`) shows the running entry's
"· N min left" line in the Approaching card; off (or `approachingCard` off) the running entry shows it instead.
The person pref `streak` (`'off' | 'flame' | 'plant'`, default `'off'`; anything else is a 400) is what the top bar
shows of the check-in streak and the plant (Settings › Focus & motivation, feature plant-companion; owner,
2026-10-26). It is not part of the theme. The person pref `syncIndicator` (boolean, default `false`; a non-boolean is a
400): off, the top bar's sync icon shows only while syncing fails; on, it shows all the time (feature header-layout).
**Flame and plant switches retired** (owner 2026-10-26): `Settings.streakFlame` and `Settings.plant` (shared, default
`true`) were replaced by the person pref `streak`. `GET /api/settings` no longer returns them and `PATCH
/api/settings` rejects either field (400 `VALIDATION_ERROR`, like `garden`).
*Migration* (once, when the server loads a `settings.json` that still has `streakFlame` or `plant`): both keys are
dropped from the stored settings and are not carried into anyone's prefs, so every person, existing or new, reads
`streak = 'off'` (the owner chose Off for everyone, whatever the switches were). No marker is needed: a person's
`streak` is only ever written by that person's own choice, and an absent value means `'off'`. Restoring an older
server backup that has the keys drops them again on load. Clients ignore the two fields in a cached copy of the
settings (last known state).
Default categories: `shopping` Shopping #0b8043 🛒, `todo` To-do #3f51b5 ✅, `work` Work #8e24aa 💼,
`home` Home #f4511e 🏠.

## Endpoints

### `GET /api/prefs` → 200, `PATCH /api/prefs` → 200

Per-person preferences (`GET/PATCH /api/prefs`, apart from `Settings`): `labs`, `approachBar`, `approachingCard`, `approachWindowHours`,
`tasksCalendarVisible`, `taskCategories`, `supportCat`, `versionInCorner` and, since the i18n slice, `language`:
`'auto' | 'en' | 'de' | 'de-x-mainfr' | 'de-x-coldmirror'`, default `'auto'` (follow the device language, feature
language). `PATCH` takes any subset, validates all fields first and answers 400 `VALIDATION_ERROR` (field `language`)
for an unknown value; it returns the full preferences.

**Minimum event length** (`prefs.minEventMinutes`, per person, feature `min-event-length`): `0 | 15 | 30`, default `0`
(off). A shorter timed entry is laid out as this long in every time view and the phone widget; the entry's real times
are unchanged. Any other value answers 400 `VALIDATION_ERROR` (field `minEventMinutes`).

**Tray width** (`prefs.trayWidth`, per person, feature `open-tasks-in-sight`): whole number of px from `260` to `560`, default `380`: the width of the desktop open-tasks side panel. Anything else answers 400 `VALIDATION_ERROR` (field `trayWidth`).

**Month scrolling** (`prefs.monthScroll`, per person, feature `month-vertical`): `sideways | vertical | vertical-snap`, default `sideways`. `vertical` stacks the
months in one list that scrolls up and down; `vertical-snap` is the same list, one month per page. Any other value answers 400 `VALIDATION_ERROR` (field `monthScroll`).

**Calendar plans** (`prefs.calendarPlans`, per person, feature `calendar-off-plan`): `{ [calendarId]: CalendarPlan }`,
default `{}`, replaced as a whole. `CalendarPlan = { windows?: { from: { day: 0-6; time: 'HH:MM' }; to: { day: 0-6;
time: 'HH:MM' } }[]; until?: 'YYYY-MM-DD'; since?: 'YYYY-MM-DDTHH:MM'; switchedAt?: 'YYYY-MM-DDTHH:MM' }` (`day` 0 =
Sunday, at most 7 windows, `from` ≠ `to`; at most 200 calendars). Times are wall times in the calendar zone. A window
is off from `from` to `to` every week; `until` is off from `since` to 00:00 of `until`; `switchedAt` is the last tap on
the calendar's switch. The server carries the plan out (ADR 0037): at a window's start, and when "off for a while" is saved, it sets the
person's `hidden` of that calendar to true; at the window's end and at 00:00 of `until` it sets it to false. Saving a
plan applies its current state at once; a restart applies an edge that passed meanwhile. A tap (`PATCH /api/calendars/:id`
`hidden`) holds until the plan's next edge. Nothing else reads the plan to decide visibility. `switchedAt` is retired:
accepted, ignored. A device offline at an edge shows the old state until its next sync. Why a pref, not the calendar:
plans are the person's choice like the other prefs and are applied for the person, whichever device is open (ADR 0023).
Anything invalid answers 400 `VALIDATION_ERROR` (field `calendarPlans`).

**Events side by side** (`prefs.daySideBySide` `1 | 2 | 3 | 4`, default `4`; `prefs.weekSideBySide` `1 | 2 | 3`, default `2`;
per person, feature event-display, owner 2026-10-25): how many overlapping entries the day / week time grid places in
columns next to each other before laying further ones over the last column; `1` is "Only 1": the earlier start-group cascade (close starts side by side,
later overlaps stacked on top). Any other value answers 400
`VALIDATION_ERROR` (field `daySideBySide` / `weekSideBySide`).

**Bedtime** (`prefs.bedtime`, per person, feature bedtime): an object
`{ enabled: boolean; mode: 'fixed' | 'dynamic'; bedtime: 'HH:MM'; wake: 'HH:MM'; weekendDifferent: boolean;
weekendBedtime: 'HH:MM'; weekendWake: 'HH:MM'; sleepMinutes: 1..960; leadMinutes: 0..480; reminderMinutes: 0..240 }`,
default `{ enabled: false, mode: 'fixed', bedtime: '23:00', wake: '07:00', weekendDifferent: false, weekendBedtime:
'00:00', weekendWake: '09:00', sleepMinutes: 480, leadMinutes: 60, reminderMinutes: 30 }`. `PATCH` takes any subset of
its fields (merged into the stored object); a wrong type, time or range is a 400 `VALIDATION_ERROR` (field `bedtime`).

### `GET /api/health` → 200

```ts
{ status: 'ok'; provider: 'mock' | 'google'; providerStatus: 'ok' | 'unavailable';
  version: string; time: DateTime; testMode: boolean }
```
Always 200 while the server runs. `providerStatus` comes from a cheap provider ping (cached ≤ 10 s; not cached while an
outage is simulated).

### `GET /api/config` → 200

```ts
{
  now: string;              // ISO UTC (toISOString), honours the test clock
  clockFrozen: boolean;     // true while a test clock is set
  timeZone: string;         // 'Europe/Berlin'
  weekStartsOn: 1;          // Monday
  pollIntervalMs: number;   // POLL_INTERVAL_MS env (default 30000), test override; 0 = polling disabled
  provider: 'mock' | 'google';
  testMode: boolean;
  publicUrl: string | null; // PUBLIC_URL env
  version: string;
  placeSearchUrl: string;   // Photon search endpoint the device asks directly (feature event-location): PLACE_SEARCH_URL env (https only), default 'https://photon.komoot.io/api'; TEST_MODE '/api/__test/photon'
  mapTileUrl: string;       // map picture template with {z}/{x}/{y}: MAP_TILE_URL env (https only), default 'https://tile.openstreetmap.org/{z}/{x}/{y}.png'; TEST_MODE '/api/__test/tiles/{z}/{x}/{y}.png'
}
```

**How the web app derives "today"**: on startup (and on every focus/visibility sync) it fetches `/api/config`.
If `clockFrozen` the app's clock is the constant `now`. Otherwise it stores `offset = Date.parse(now) - Date.now()` at
fetch time and uses `Date.now() + offset`. "Today" is the date of that instant in `timeZone`. If `/api/config` fails
(offline), the app uses the device clock, `Europe/Berlin`, Monday, 30 s polling. All date logic in `web/` goes through
one `useClockStore()` composable; nothing else calls `new Date()` for "now".

### `GET /api/release-notes` → 200

`{ notes: { id: string; date: 'YYYY-MM-DD'; text: string }[] }`, newest first, at most 50: every `- ` bullet under a
`## YYYY-MM-DD` heading of `CHANGELOG.md` (`CHANGELOG_PATH`) up to `## Older history`, read once at start. `id` is a
short hash of date and text. A missing or unparsable file gives an empty list.

### `GET /api/calendars` → 200

`{ calendars: Calendar[] }` — every calendar in the person's Google list (own and shared), plus one virtual calendar
`{ id: 'birthdays', name: 'Birthdays', virtual: true, writable: false, primary: false, defaultReminders: [] }` (ADR 0038): every
birthday event (`eventType` birthday, any `birthdayProperties.type`) of the person's calendars and the events of Google's old contacts
calendar (`addressbook#contacts@...`, also when Google marks it hidden). That contacts calendar is never listed itself. The events
of the virtual calendar carry `calendarId: 'birthdays'` (their real calendar stays server-side; edits go by event id). The virtual
calendar's `color` is the person's own choice (default `#9fc6e7`), stored in the app, not in Google. Each calendar has
`hidden: boolean` (the person's choice) and `defaultReminders: number[]` (the popup lead times of the calendar's Google default, minutes, Google's order). The virtual `birthdays` also has `contactsPermission` (`granted` when the stored token's scope includes `contacts.readonly`, else `missing`; the device keeps it with the calendar list, so the offer in the settings works offline). Errors: 503.

The virtual calendar also holds the birthdays read from Google Contacts (feature contact-birthdays, ADR 0043; only with `contactsPermission: 'granted'`), see "Birthdays from Google Contacts" below.

### `GET /api/calendar-colors` → 200

`{ colors: Array<{ id: string; background: string; foreground: string }> }`: Google's calendar colour palette (`colors.get`, the
`calendar` map: ids `1`..`24`), the same for everybody. The server asks Google once per process and keeps the answer; when Google
cannot answer it sends the built-in copy of the 24 (`shared/colors.js`, not kept). The change feed carries the same answer as the
per-person file `calendarColors`, so the app has the palette on the device (it shows the built-in copy before the first sync).

### `PATCH /api/calendars/:id` → 200

Body `{ hidden?: boolean; defaultReminders?: number[]; color?: string; colorId?: string }` (at least one). `hidden` stores the
person's choice (for `birthdays` too: the same per-person flag, so plans and `excludeHidden` apply). On `birthdays`, `color` and
`colorId` store the person's colour in the app (nothing goes to Google) and `defaultReminders` is `400`. `colorId` (an id of `GET /api/calendar-colors`; anything else `400`) sets one of Google's calendar colours as the
person's calendar list colour, written as that colour's RGB like a custom one (Google lets an RGB colour already on the list entry
supersede a bare `colorId`, so a `colorId` alone would not change what is shown). `color`
(`#rrggbb`, answered lower-case; anything else `400`) is a custom colour: `calendarList.patch` with `colorRgbFormat=true`,
`backgroundColor` = `color`, `foregroundColor` = black or white, whichever reads better (Google then clears or re-derives the
palette id). `color` together with `colorId` is `400`. Both work for every calendar in `GET /api/calendars`, also one the person
cannot edit (Google keeps the list colour per person), and recolour the `color` of the calendar's events that follow it
(`colorId` null, see `CalendarEvent`); no server-wide copy exists. The Color row of the calendar's settings page offers the
palette, the current colour, a colour picker and a hex field (feature calendar-colours). `defaultReminders`
(at most 5 different whole numbers 0-40320) replaces the calendar's popup defaults in Google (`calendarList.patch`; email defaults
stay; more than 5 reminders in all is `400`). Returns the updated `Calendar`. 404 for an unknown id.

**Read-only calendars.** `defaultReminders` on a calendar without writer/owner role goes to Google exactly like on a writable
calendar (`calendarList.patch`: Google stores a calendar's notifications per person, also for calendars the person cannot edit).
A Google error surfaces like any other save error; the app keeps no copy. Why: the owner, 2026-10-23: "the app should not ask
google ... behaviour that we know fails" (requirements 20261023T073351Z_readonly_reminders_no_google).

### `GET /api/holiday-regions?lang=de|en` → 200

`{ regions: Array<{ code: string; variants: Array<'official' | 'all'>; added: Array<'official' | 'all'> }> }`: the countries of the
curated list (`server/src/providers/holidayRegions.ts`, ISO 3166 `code`, ADR 0039) whose Google holiday calendar exists in the
language `lang` (default `en`; any other value falls back to `en`). `variants` are the variants that exist (`official` = public
holidays only, id `<lang>.<region>.official#holiday@group.v.calendar.google.com`; `all` = holidays and observances, id
`<lang>.<region>#holiday@group.v.calendar.google.com`); `added` are the variants the person already has in their Google list (in any
language). Every id is checked with `calendars.get` before it counts (a 404 falls back to a one-event `events.list`, both 404 = the
id does not exist); the answer of each id is kept in the process for 24 h, a failed check (outage, rate limit) is not kept and
makes the whole call `503`. A country with no existing variant is left out. Country names are not sent: the app names a `code`
in its own language (`Intl.DisplayNames`).

### `POST /api/holiday-calendars` → 201 | 200

Body `{ code: string; variant: 'official' | 'all'; lang?: 'de' | 'en' }`. Subscribes the person to that holiday calendar:
`calendarList.insert` with the id built by the server (never a client-supplied id) and `selected: true`. Returns the `Calendar`
(`holiday: true`). `400` for a `code` outside the curated list or an unknown `variant`; `404` when Google has no such calendar;
`200` with the existing entry when the person already has that region and variant (in any language). The person's other devices
get it through the `calendars` and `events` change kinds.

### `DELETE /api/holiday-calendars/:id` → 204

Removes a holiday calendar from the person's Google list (`calendarList.delete`; the public calendar itself is untouched) and
clears the person's stored switch for it. `:id` is URL-encoded (it contains `#` and `@`). `404` when the id is not a holiday
calendar (`#holiday@group.v.calendar.google.com`) of the person's list; no other calendar can be removed this way.

### `GET` / `PATCH /api/reminders/tasks-calendar` → 200

The person's tasks calendar is not in `GET /api/calendars`; its popup default list is read and replaced here:
`{ defaultReminders: number[] }` (PATCH body the same).

### Reminders on events and task lists

`CalendarEvent` and `TaskList` carry `reminders: { useDefault: boolean; minutes: number[] }` (absent on shared lists). `minutes`
is the popup list in effect: the calendar's default while `useDefault`, else the item's own Google `overrides` of method
`popup`. `POST` / `PATCH` of an event or task list accept the same object (at most 5 different whole minutes 0-40320;
`useDefault: true` ignores `minutes`); a write keeps the item's non-popup (email) overrides, and a `PATCH` without
`reminders` leaves them alone. Why: Google is the source of truth (feature reminders).

**Read-only events.** A `PATCH` whose body holds nothing but `reminders` is allowed on an event with `readOnly`. In a calendar
shared read-only the server never asks Google (Google has no per-event reminders there; its UI offers notifications only for
the whole calendar): it keeps the person's reminders for that event itself (`DATA_DIR/users/<sub>/reminder-overrides.json`,
`{ events: { calendarId: { eventId: Reminders } } }`, in the Drive backup) and shows the kept list as the event's `reminders` on
every read. Files of the older format (path memory, kept defaults) are read for `events` only. An invitation in the person's own
calendar (read-only by its organizer) still goes to Google, which stores `reminders` per person. Any other field in the body is
still `403 calendar.event.notOwn`. Why: owner decision of 2026-10-23, see ADR 0015 addendum. Birthdays are not covered.

### Web Push

Per person (`local` while sign-in is off); all `204` unless noted. Why: feature reminders, slice 2.

- `GET /api/push/key` → `200 { key }`: the server's public VAPID key (URL-safe base64).
- `POST /api/push/subscriptions` `{ endpoint, keys: { p256dh, auth } }`: stores a browser's subscription (an `https` endpoint of a real push service: `fcm.googleapis.com`, `*.push.services.mozilla.com`,
  `web.push.apple.com`, `*.notify.windows.com`, port 443, no IP literal, else `400`; TEST_MODE also accepts `push.example.test`; same
  endpoint again updates its keys and keeps its plan; at most 10 per person, else `400`).
- `DELETE /api/push/subscriptions` `{ endpoint }`: removes it (also when unknown).
- `PUT /api/reminders/plan` `{ endpoint, plan: { at, title, body, key, kind? }[] }`: replaces that browser's plan (`at` epoch ms, at most
  500 entries; `kind`, when known, one of `event`, `tasklist`, `summary`, `bedtime`, which the service worker shows with its own
  icon, else `400`; an entry without it, from an older web app, shows as an event).
  `404` when the endpoint is not subscribed. The server sends `{ title, body, key, kind }` (`kind` when the entry has one) at `at`, up to 10 minutes late,
  once per `key`, from one timer loop on the app clock; a `404`/`410` from the push service removes the subscription. Every send has a
  10 s timeout and each browser is served on its own, so one endpoint that never answers holds back nobody.

### `GET /api/changes[?cursor=<opaque>][&today=YYYY-MM-DD]` → 200 (device sync, ADR 0025)

What changed for the signed-in person since the device's cursor. Without a cursor, or with one that is not ours (also one made for another person, or one from before
the shape of stored events last changed) or is unreadable, everything the device keeps is answered in full (`full: true`). `today` is the device's date; it defaults to the
app clock's today and is ignored (the server's today is used) when it is more than 3 days away from it.
The cursor is opaque to the app: send back the `cursor` of the last answer you applied. It is per device (it holds the
state of that device's last answer; two devices of one person sync independently) and is only a position, never a
secret. Apply an answer in this order: `calendars`, then per kind the `replace` / `series` / `removed` drops, then
`upserts`, then `files`.

```json
{
  "full": false,
  "cursor": "eyJ2IjoxLi4u",
  "window": { "from": "2025-10-12", "to": "2027-10-13" },
  "calendars": [ /* every event calendar, as GET /api/calendars (with `hidden`); always in full */ ],
  "events": {
    "calendars": ["primary", "work"],
    "replace": ["work"],
    "series": [{ "calendarId": "primary", "seriesId": "abc" }],
    "removed": [{ "calendarId": "primary", "id": "def" }],
    "upserts": [ /* CalendarEvent, as GET /api/items */ ],
    "failed": []
  },
  "taskLists": { "replace": false, "series": ["abc"], "removed": ["def", "shared:x1"], "upserts": [ /* TaskList */ ], "failed": false },
  "files": { "prefs": { }, "settings": { } }
}
```

- `window`: events a device keeps are those overlapping `[from, to)` (today minus a year to today plus a year, end
  exclusive). Events outside it are never in `upserts`; one that moved out is in `removed`. As days pass, the events
  entering the window arrive in `upserts` of the next answer (up to 31 days behind; further behind, the calendar is
  answered as `replace`).
- `events.calendars`: the event calendars that exist now. The device drops the events of any other calendar.
- `events.replace`: calendars answered in full (first sync, an expired Google sync token (410), a calendar new to the
  device, or the person's own reminders on read-only events changed). The device drops that calendar's events first. An
  expired token is never an error.
- `events.series` / `taskLists.series`: repeating events whose stored instances the device drops before applying
  `upserts` (their current instances inside the window are in `upserts`).
- `events.failed` / `taskLists.failed`: calendars (the tasks calendar) that could not be read this time. The device keeps
  its copy of them, their position in the cursor is unchanged, and the next call tries again; the rest of the answer is
  complete. While a calendar failed, the cursor keeps its old window end and reminder version, so the missed days and relist
  are retried. Person-wide failures (rate limit, sign-in again, missing calendar permission) and unexpected errors (bugs)
  still fail the whole call.
- A calendar Google keeps refusing is not asked on every call: one that is gone (404) or no longer readable (403
  permission) is answered `failed` once, and a calendar whose fresh sync token is refused a second time in a row (410
  right after its full read) is answered unchanged. Either is then left alone (answered unchanged, no Google call) for
  1 minute, doubling per refusal in a row up to 30 minutes, shared by every device and the live poll; the first read
  after the wait is in full (`replace`). A working token clears the back-off. Each back-off writes one
  `google_calendar_backoff` log line (hashed calendar id, cause, wait).
- A calendar whose fresh sync token Google refused (some of Google's own calendars, e.g. public holidays, never accept
  one) is no longer asked with a token: after its back-off every call lists its window and compares it with what the
  device got last (a content version in the cursor). It is answered as `replace` only when that changed, otherwise
  unchanged; it costs one list call per call and no further 410s. The server forgets this on a restart and learns it
  again from the next refusal; a version left in a cursor is never sent to Google as a token.
- A repeating event that became a plain one is listed in `series` (the device drops its old instances) and its plain
  event is in `upserts`. When more than 20 repeating events of one calendar changed in one call, that calendar is
  answered as `replace` instead of one Google call per series.
- `events.removed`: deleted or moved away (the same id may come back in `upserts` for the new calendar, so apply drops first).
- `taskLists`: all of the person's task lists, of any date and undated ones included, plus shared lists. `replace` is
  true when the tasks calendar was answered in full: the device drops all its own (non-`shared:`) lists first; shared
  lists are always compared one by one. `removed` holds ids, shared lists that were deleted, left or unshared included.
  A repeating list contributes its instances inside the window.
- `files`: per-person data, each part present only when its version (a hash of what the app would show) moved since the
  cursor, and then in full. Names: `settings` (as `GET /api/settings`), `prefs` (`GET /api/prefs`), `theme`
  (`GET /api/prefs/theme`), `themes` (`GET /api/themes`), `templates` (`GET /api/templates`), `widgetKeys` (`{ keys }` as `GET /api/widget-keys`, never a key itself), `canvas`
  (`GET /api/canvas`), `motivation` (`GET /api/motivation`), `categoryShares` (`GET /api/categories/shares`), `people`
  (`GET /api/people`), `tasksCalendarReminders` (`GET /api/reminders/tasks-calendar`), `calendarColors` (`GET /api/calendar-colors`).
- A repeated call with the cursor of its own answer, with nothing changed, answers empty parts.
- Google cost: one list call per calendar per call (the sync token), plus one `events.instances` call per changed
  repeating event (at most 20 per calendar); a first or `replace` answer costs two list calls per calendar. The token
  of an event calendar comes from a token-only walk of its pages (no time range or filters, which Google refuses together
  with a sync token; at most 200 pages). A calendar too large for that is answered as `failed` and not tried again for
  10 minutes. The rate guard applies: while Google
  rate-limits, the answer is `503 RATE_LIMITED` with `Retry-After`, as for `GET /api/items`; the device keeps its data
  and shows no banner.
- Errors: `400` for a bad `today`.

### `GET /api/items?from=YYYY-MM-DD&to=YYYY-MM-DD[&calendarIds=a,b]` → 200

Returns every event and task list overlapping `[from 00:00, to 00:00)` local time (`to` exclusive), from all calendars
(or the listed ones).

```ts
{ items: CalendarItem[]; from: LocalDate; to: LocalDate; syncedAt: DateTime; failed?: string[]; stale?: true }
```
`failed` lists the calendars Google could not read this time (as `events.failed` of `GET /api/changes`); their items are missing and
the web app reads the period again at the next sync. Only when every calendar failed does the request fail (502/503).
`stale: true` (see "Stale data") means the items came from the server's cache while Google's rate limit was in force.
Sorted by start (all-day first per day, then by time, then title). A Google event whose
`extendedProperties.private.kind === 'tasklist'` is returned as `TaskList`, all others as `CalendarEvent`. Cancelled
events are omitted. Errors: 400 (`from`/`to` invalid, `to <= from`, range > 100 days), 503, 502.

Optional `&also=YYYY-MM-DD..YYYY-MM-DD` (one extra range, same rules) adds that range's items to the same response, so
the client's poll stays one request when it also keeps today loaded for the Approaching card (owner, 2026-10-13;
alternatives weighed: two requests per poll — breaks the polling budget; refreshing today less often — staler card).
The response then also carries `also: { from, to }`; items present in both ranges appear once.

Optional `&excludeHidden=1` leaves out the items of the calendars the signed-in person switched off (`PATCH /api/calendars/:id`).
The web app filters hidden calendars itself, instantly; the Android widget fetches this endpoint natively, cannot see
that state, and sends the flag (owner bug 2026-10-14: hidden calendars showed in the widget). A calendar whose plan has
it off is left out too, because the plan's scheduler sets `hidden` (see "Calendar plans").

### Widget keys and the iPhone widget data (ADR 0044; feature iphone-widget)

A person creates a read-only key per device in Settings; the Scriptable widget on that iPhone presents it. Keys are per
person: every route below lists and changes only the signed-in person's keys, and the widget data is that person's.

| Method | Path | Body | Success |
|---|---|---|---|
| `POST` | `/api/widget-keys` | `{ name }` (1-40 characters, the device name) | `201` `{ id, name, createdAt, lastUsedAt: null, key }` |
| `GET` | `/api/widget-keys` | – | `200` `[{ id, name, createdAt, lastUsedAt }]` (never the key) |
| `DELETE` | `/api/widget-keys/:id` | – | `204` |

- These three need the normal session. `key` is in the `201` answer only (`Cache-Control: no-store`) and cannot be read again.
  At most 10 active keys per person (else **409 `WIDGET_KEY_LIMIT`**); an unknown or foreign `:id` answers **404**.
- `key` has the form `cwk_<id>_<secret>`: `id` 8 characters `[A-Za-z0-9_-]` (also the list's `id`), `secret` 256 random bits,
  base64url. The server stores `id`, `name`, `createdAt`, `lastUsedAt` and the SHA-256 of `secret` (never the secret) in
  the person's `widget-keys.json`. A revoked key keeps its record (hash, `revokedAt`) for 90 days so the widget can say
  "removed"; after that it answers as unknown.

`GET /api/widget/script` → 200 `text/javascript`

- Key-authenticated like the data route (same errors, same rate limit). The body is the widget script, the same for every
  person and **with no secret and no person in it**: it reads the key and the server URL from Scriptable's Keychain, where the
  installer put them. First line `// calendar-widget version=<n>`; `Cache-Control: no-store`.
- Tiny installer (generated in the app, shown with "Copy installer"): holds the key and the server URL, stores both in the
  Keychain, requests this route and saves the body with `FileManager.writeString` as a script in the documents
  directory, so it appears in Scriptable's list. It tells the person what to do next ("Add a Scriptable widget").

`GET /api/widget/data?from=YYYY-MM-DD&to=YYYY-MM-DD` → 200

- The routes a key opens are this and `/api/widget/script`: header `Authorization: Bearer <key>`. A key on any other `/api/*` route answers **401
  `UNAUTHENTICATED`**; the session cookie on this route is ignored (also **401**). Read-only by construction: no other method
  is routed for a key.
- Answer `{ generatedAt, today, scriptVersion, items, minEventMinutes, weekSideBySide, taskCategories, widgetCircle, widgetLayout, widgetTimelineDays, language }`: `items` as `GET /api/items` for the
  range with `excludeHidden=1` always on (the same function and the same shared visibility rule, hidden flag and plans
  included; the key cannot turn it off), the five prefs as `GET /api/prefs` gives them (`language`: the person's app language, so the widget speaks it; `auto` means the iPhone's, and anything but German or English reads as English; `widgetLayout`: `standard` (default) or `timeline` (the medium and large iPhone widgets draw days as columns from today) and `widgetTimelineDays`: 1 to 7, default 3 (the Timeline's day count), both per person and validated like the other prefs; `widgetCircle`: `time` (default) or `countdown`, the lock-screen circle's drawing, per person, validation field `widgetCircle`; the script keeps the answer, setting included, for offline). `to - from` at most 14 days (the script asks for the week and the days around it, so one cache serves every size).
  `scriptVersion` is the newest script's `version`; a script that is older fetches `/api/widget/script`. `today` is the calendar's local date, so the script needs no time zone logic.
- Errors: **401 `WIDGET_KEY_INVALID`** (missing, malformed or unknown key), **401 `WIDGET_KEY_REVOKED`**, **400** (range as for
  items, at most 14 days), **429 `RATE_LIMITED`** with `Retry-After` (at most 30 requests per key per minute; a revoked or unknown key is
  limited per client address too), 503/502 as for items. A good answer sets `lastUsedAt` (written at most once per hour).
- The key list also travels in `GET /api/changes` as the `widgetKeys` file, so Settings shows it offline (the secret never does).
- Keys are not part of the person's backup or restore; a lost key is simply created again.
- Not cached by shared caches (`Cache-Control: no-store`). The script keeps the last answer on the phone.

### Events

| Method | Path | Body | Success |
|---|---|---|---|
| `POST` | `/api/events` | `CreateEventInput` | `201` `CalendarEvent` |
| `GET` | `/api/events/:id` | – | `200` `CalendarEvent` |
| `PATCH` | `/api/events/:id` | `UpdateEventInput` | `200` `CalendarEvent` |

```ts
interface Place { name: string; lat: number; lon: number }  // name 1–200 chars after trim; lat -90..90, lon -180..180 (WGS 84)

interface CreateEventInput {
  calendarId?: string;     // default: primary calendar
  title: string;
  description?: string;
  location?: string;       // with a picked place: "<name>, <address>"
  place?: Place | null;    // stored in Google's private extended properties placeName/placeLat/placeLon only while `location` is the name or starts with "<name>, " (else dropped); PATCH: null drops it, absent keeps it (a new location must still match)
  allDay: boolean;
  start: DateTime | LocalDate;
  end: DateTime | LocalDate;   // must be > start (all-day: exclusive date > start date)

```

#### Birthdays

Birthdays made in Google Calendar (`eventType: "birthday"`, a yearly all-day event in a normal calendar) are handled like
Google Calendar handles them (feature birthdays).

`POST /api/events` with `kind: 'birthday'` creates one in the person's primary calendar (`201` `CalendarEvent`, the series
as created; `403` when the primary calendar is read-only):

```ts
interface CreateBirthdayInput { kind: 'birthday'; title: string; date: LocalDate; colorId?: string | null }
```

Nothing else is accepted (`400`, unknown field). The server sends Google exactly: `eventType: 'birthday'`, a one-day
all-day `start`/`end`, `recurrence: ['RRULE:FREQ=YEARLY']` (29 February: `['RRULE:FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=-1']`),
`visibility: 'private'`, `transparency: 'transparent'`, `birthdayProperties: { type: 'birthday' }`, `summary` and the
optional `colorId`; Google rejects any other property on a birthday.

`PATCH /api/events/:id` on a birthday (the id of any year's instance) changes the whole yearly series, never one year:
only `title`, `colorId` and a one-day all-day `start`/`end` (`allDay: true`, `end` = `start` + 1 day; only its month and
day are used, the series keeps its start year, i.e. the birth year) are accepted. `description`, `location`, `reminders`, `calendarId` and `allDay: false` answer `400`
(`calendar.birthday.field`). A new date on a `dateLocked` birthday answers `400` (`calendar.birthday.dateLocked`); a move onto or off 29 February
answers `400` (`calendar.birthday.leapDay`: the yearly rule would have to change, which a patch cannot). The
answer is the opened instance (same `id`) with the change applied. `DELETE` removes the whole series (Google does not touch
Contacts). `If-Match` is checked against the instance.

Editing follows Google's permissions: only events in calendars the person may write (role owner or writer, whoever owns the calendar, e.g. the family calendar or another person's calendar shared with edit rights; an event whose organiser is its calendar is not an invitation) are editable: `PATCH`/`DELETE` of an ordinary event with `readOnly` answer `403 FORBIDDEN`
(`calendar.event.notOwn`), as do `POST` into a calendar that is not editable and a `PATCH` moving an event into one (`calendarId`).
The checks come before `If-Match`.

Birthdays with `readOnly` (the contacts Birthdays calendar, calendars that are not the person's own) answer `PATCH` and `DELETE`
with `400 VALIDATION_ERROR` ("Birthdays are read-only"). A birthday's colour is its own `colorId`, else its calendar's
(the contacts calendar's entries always show the calendar colour).

#### Birthdays from Google Contacts

With `contacts.readonly` (feature contact-birthdays, ADR 0043) the server also reads the person's contacts and adds their
birthdays to the virtual `birthdays` calendar. Nothing is written to Google Contacts or Google Calendar. The `CalendarEvent`s
are made on the server, like a calendar birthday:

- Source: People API `people.connections.list` for `people/me`, `personFields=names,birthdays,events`, `pageSize=1000`, all
  pages, `requestSyncToken=true`. The server keeps the `nextSyncToken` per person and asks only for changes after the first
  full read (deleted contacts come back with `metadata.deleted`; the token expires after 7 days: the error reason
  `EXPIRED_SYNC_TOKEN` is answered with a full read). Every dated entry counts: `birthdays` (with a `date`; the
  deprecated free-text `text` alone does not) and `events` (`type` anniversary, or a custom label, or `other`). A contact without a
  display name is skipped. Titles: a birthday and an anniversary are the contact's display name (an anniversary is marked
  like a calendar anniversary: `special: 'anniversary'`, the ring); a custom date is `<label>: <name>` and an `other` one is
  `<name>`, both without `special` (no marker).
- A birthday with a year gives `contactBirthday.birthYear` (only birthdays: anniversaries and other dates have none, so no age);
  every date repeats every year, also one with year 0 or none. 29 February
  falls on the last day of February in years without one, as for calendar birthdays.
- Events: all-day, `calendarId: 'birthdays'`, `special: 'birthday'` (`'anniversary'` for an anniversary; absent for other dates), `readOnly: true`, `readOnlyReason: { kind: 'contact' }`,
  `id` = `contact:<resourceName>:<entry>:<YYYY-MM-DD>` (`<entry>` is `b` for the birthday, `e<n>` for the n-th other date; one per year inside the window, like a repeating series), the calendar's
  colour. `PATCH` and `DELETE` answer `400 VALIDATION_ERROR` ("Birthdays are read-only"), as for the old contacts calendar.
- One birthday shows once: a contact date is dropped when a calendar birthday event of the same kind has `birthdayProperties.contact` equal
  to the contact's resource name, else the same title (case-insensitive) on the same day. Contacts with the same name on
  different days both show. The calendar event wins (it is the editable copy).
- Failure is never a sign-in or calendar failure: when the People API answers an error or the scope is missing (403), the
  other birthdays and events are answered as before and no error reaches the app; the next sync tries again.
- Change feed (ADR 0025): contact birthdays travel as events in `upserts` / `removed` of the `birthdays` calendar; a change
  of a contact (renamed, date changed, deleted) shows with the next sync. `calendars` carries `contactsPermission`, so
  granting it changes the answer; the first answer after granting is a full one for `birthdays`.
- Per person: the sync token and the events belong to the person's own token (`users/<sub>/`); nothing is shared.
- The scope is not asked at sign-in and nobody is signed out: while `contactsPermission` is `missing` the app shows the standard snackbar
  `contacts-offer` (`ui.notify`, `duration: 0`, the pattern of the APK hint) "Show birthdays from your Google Contacts too?", whose
  action "Allow" goes to `GET /api/auth/google/start?contacts=1` (also while signed in), which adds
  `https://www.googleapis.com/auth/contacts.readonly` to the scopes with `include_granted_scopes=true`, so the grant adds to
  the old ones; the callback returns to `/` (with `&to=settings` to `/settings/calendars/birthdays`, the Birthdays settings
  page, which offers the same link while the permission is missing, also after the snackbar was dismissed). The snackbar stops when the permission is granted; its ✕ means not now, for good: `prefs.contactsOfferDismissed` (boolean, per person, default `false`, any other value `400` field
  `contactsOfferDismissed`); it is not shown again, also on other devices. A person who leaves Google's checkbox unticked
  stays at `contactsPermission: 'missing'` and nothing else changes.

| `DELETE` | `/api/tasklists/:id` | – | `204` |
| `POST` | `/api/tasklists/:id/items` | `{ id?: string; title: string; done?: boolean; index?: number }` | `201` `TaskList` |
| `PATCH` | `/api/tasklists/:id/items/:itemId` | `{ title?: string; done?: boolean }` | `200` `TaskList` |
| `DELETE` | `/api/tasklists/:id/items/:itemId` | – | `200` `TaskList` |
| `PUT` | `/api/tasklists/:id/items/order` | `{ itemIds: string[] }` | `200` `TaskList` |

```ts
interface CreateTaskListInput {
  // no calendarId: task lists always go to the person's tasks calendar (feature tasklists-own-calendar)
  title: string;          // may be empty/blank (stored as "") when at least one non-blank item is given
  date: LocalDate | null; // required key; null creates an undated list (no time, no recurrence)
  time?: LocalTime | null;
  items?: { title: string; done?: boolean }[];   // blank titles are dropped
  categoryId?: string | null;   // must exist in settings, else 400
  tags?: string[];
  estimateMinutes?: number | null;
  recurrence?: 'daily' | 'weekly' | 'monthly' | null;
}
interface UpdateTaskListInput {
  title?: string;
  date?: LocalDate | null; // a date makes the list appear in the calendar; null makes it undated (drops the time)
  time?: LocalTime | null; // null removes the time
  items?: { id?: string; title: string; done: boolean }[];  // full replacement (used by fixtures)
  categoryId?: string | null;
  tags?: string[];
  estimateMinutes?: number | null;
  canvas?: { x: number; y: number } | null; // x, y integers 0-10000 (else 400, field `canvas`); null clears the place
}
```
Item ops return the whole updated `TaskList`. On a repeating list every occurrence is ticked on its own (owner,
2026-10-23: "split on first tick"): an item op on an occurrence id patches that Google instance (an exception from then
on, also when unticked again), and an item op addressed to the series id (the master, which only `GET /api/tasklists/:id`
with that id hands out) goes to its first occurrence the same way; the answer is then that occurrence, with
its own `id`. The master's items never change by an item op. When the first occurrence is no longer on the master's start day
(deleted, or moved to another day), an item op addressed to the series id answers 404 `Task list not found` and changes
nothing. Creating a repeating list answers with its first occurrence (the id range reads list, with `seriesId`), so a
client never holds the series id from a create; the web app deletes a repeating list it created in this session as a
whole series (`DELETE` of its `seriesId`), any other occurrence on its own. Deleting the series removes its
split-off occurrences too (Google). `PATCH` / `DELETE /api/tasklists/:id` keep addressing exactly the given id (series or occurrence). **This and all following** (owner, 2026-10-24, feature
tasklist-repeating; Google's "This and following events"): `?scope=following` on `PATCH /api/tasklists/:id` (body `title`
only), `POST /api/tasklists/:id/items`, `PATCH /api/tasklists/:id/items/:itemId` (body `title` only) and
`DELETE /api/tasklists/:id/items/:itemId` changes the occurrence `id` and every later one of the list; earlier ones never
change. A list is one or more Google series ("parts") sharing `seriesKey` (the first series' id; later parts carry it as
the private property `series`). The Calendar API has no "this and following" operation; the server does what Google
Calendar's own does, splitting the series, using only documented calls:
(1) every part that starts after the given occurrence gets the change as a whole: the series and each live exception,
each by read-modify-write (ticks kept); (2) in the part holding the occurrence — when it is that part's first one, the
whole part changes the same way and nothing is split; otherwise (3) the occurrence gets the change (an exception of the old
series from then on); (4) a new series starts at the earliest later occurrence of the part by rule date (the next live
one within 62 days — 400 when the part has no end — or any later exception, also a moved or a deleted one), with the
part's data plus the change, the part's RRULE and EXDATE lines (so it keeps the part's end; an RDATE stays with the old part) and `series`; a series an earlier,
unfinished try made at that date is used again; (5) every later exception of the part (read without `singleEvents`, with
`showDeleted` and without a property filter, since Google guarantees only `id`, `recurringEventId` and `originalStartTime`
on a cancelled exception) is carried over to the new series' occurrence of the same rule date — its own data (ticks, own
times, reminders) plus the change, a deleted one deletes the new series' occurrence only when this request made the new series and
did not carry that date itself (a reused series never loses a week; a week deleted in the old series may then come back
once); a live one whose week was already deleted
in the new series (a half-done split showed it twice) answers 409 `CONFLICT` (key `tasklist.showsTwice`, `details: [{ field: 'date', issue: <date> }]`)
`This list shows twice on <date>; delete the other copy, then try again` and changes nothing more — and the old exception is deleted; one that cannot be carried
answers 502 before anything is ended; (6) last, when no later live exception is left in the part, its RRULE line gets
`UNTIL` = the occurrence's start (date for all-day, UTC for timed; any UNTIL/COUNT replaced, other lines such as EXDATE
kept), written with If-Match (re-read and retried up to 3 times, else 412). A failure midway can leave duplicates, never a
lost list; repeating the request finishes it. A part whose rule has `COUNT` is not split → 400 (field `scope`). A part
without an end and no later occurrence within 400 days → 502. A later write of a series keeps its rule when the rhythm
is the same (its UNTIL stays). An added item gets one id, unticked; `POST .../items` may name it (`id`, 8-21 of `A-Za-z0-9_-`; the web app does for
"following"), and a list that already holds that id stays as it is, so a repeated request adds it once; a text change / removal reaches the lists that hold
that item id. The answer is the given list (same `id`) after the change. The door board groups by `seriesKey`; deleting
a series also deletes its later parts (same `series`, later start). `scope=following` on a list that does not repeat →
400 `This list does not repeat` (field `scope`); with other fields than `title`, or `done` on an item → 400 (field
`scope`); any other `scope` value than `this` / `following` → 400. Without `scope` (or `scope=this`) only the
given id changes, as above. `index` inserts at a position (default: append). `itemIds` must be a
permutation of the current ids, else 400. A list with an empty title and no items left → 400 `Add a title or an item`. Blank item titles → 400 (the UI ignores blank input without calling the API).
Errors: 400, 404 (unknown list or item, or id is a plain event), 412 (`PATCH`/`DELETE` of the list with stale
`If-Match`), 502, 503.

### Shared task lists (owner, 2026-10-14; feature shared-lists)

A shared list lives in the server's shared store, not in Google. It is served through the **same task list endpoints**
as every list, under an id with the prefix `shared:` (`shared:<id>`); everything above (items, ops, `If-Match`,
`/api/items`, `/tasklists/open|all-open|archive`, `/summary`) works on it for the owner and for every member. A shared
list has `calendarId: "shared"` and an optional field on `TaskList`:

```ts
interface Person { sub: string; name: string; email: string; initial: string }   // initial: first letter, upper case
interface SharedInfo { owned: boolean; owner: Person; with: Person[] }          // `with`: everyone but the requester
// TaskList.shared?: SharedInfo   (absent on lists that are not shared)
// TaskList.etag of a shared list: the version counter, e.g. "7"; every write bumps it
// TaskList.categoryId / color: the OWNER's category, carried on the list (a member sees its name, colour and icon via `categoryInfo`)
// TaskList.categoryInfo?: { name: string; color: string; icon: string | null } | null   (shared lists only)
```

| Method | Path | Body | Success |
|---|---|---|---|
| `GET` | `/api/people` | – | `200` `{ people: Person[] }`: the allowed people who signed in at least once, without the requester |
| `POST` | `/api/tasklists/:id/share` | `{ person: string }` (the person's `sub`) | `200` `TaskList` (a Google list is moved into the shared store: new id `shared:...`; on a shared list the owner adds a member) |
| `DELETE` | `/api/tasklists/:id/share` | – | `200` `TaskList` (owner only: the list moves back into the owner's tasks calendar, new Google id; members lose it) |
| `POST` | `/api/tasklists/:id/leave` | – | `204` (member only: removes the list for the caller) |
| `GET` | `/api/categories/shares` | – | `200` `{ shares: Record<categoryId, Person> }` |
| `PUT` | `/api/categories/:id/share` | `{ person: string \| null }` | `200` `{ shares }`: shares the category (all its lists move, new lists are created shared) or, with `null`, unshares it (its lists move back) |

Rules:
- Every shared-list call checks that the caller is the owner or a member: anyone else gets `404` (the list's existence
  is not revealed). Owner-only actions (`DELETE /api/tasklists/:id`, `DELETE .../share`, adding a member) answer `403
  FORBIDDEN` to a member. A member removes a list for themselves with `leave`; `DELETE` deletes it for everyone (owner).
- A member must be a person who may use the app (the allow-list) and has signed in once; anything else is `400`. So is
  sharing with yourself, sharing a repeating list (`recurrence` is not stored on shared lists) and sharing while sign-in
  is off.
- A member may change everything of a shared list except its category (`400`, key `sharing.categoryOwnerOnly`).
- Writes with a stale `If-Match` (list `PATCH`/`DELETE`) answer `412 PRECONDITION_FAILED` (the existing conflict
  message). Item ops and unpinned writes never conflict: they read the latest version and apply on top of it.
- Moving in or out keeps title, items, ticks, date/time, tags, estimate, category, `completedOn` and the canvas place.

### Settings and categories

Stored server-side per person in `DATA_DIR/users/<sub>/settings.json` (`users/local/` while sign-in is off;
independent of the provider; atomic writes; ADR 0035). Each person who signs in has their own settings and categories:
a change by one person never changes what another reads, and `version` (the `If-Match` value) counts that person's
changes only. A person without a file reads the defaults (the four categories); nothing is written until they change something, so
opening the app creates no data of their own (Drive backup, restore at sign-in). A shared
task list still shows the owner's category to its members (`categoryInfo`, see Shared lists).

*Migration from the server-wide file* (once, on the first start after the update): a `DATA_DIR/settings.json` and
`DATA_DIR/motivation.json` from before are copied to every known person (`people.json`, the folders under `users/`, and
`local`) who has no file of their own yet, then renamed to `settings.json.bak` / `motivation.json.bak`. Without the old
file nothing happens, so it runs once; an interrupted run finishes on the next start; a person's own file is never
overwritten. A Drive backup made before the split carries them as `server/settings.json` / `server/motivation.json`:
a restore gives them to the person whose backup it is unless the backup also holds the person's own file.

| Method | Path | Body | Success |
|---|---|---|---|
| `GET` | `/api/settings` | – | `200` `Settings` |
| `PATCH` | `/api/settings` | `Partial<Omit<Settings, 'categories' \| 'updated' \| 'version'>>` | `200` `Settings` |
| `POST` | `/api/categories` | `{ name: string; color: string; icon?: string \| null }` | `201` `Settings` |
| `PATCH` | `/api/categories/:id` | `{ name?; color?; icon? }` | `200` `Settings` |
| `DELETE` | `/api/categories/:id` | – | `200` `Settings` |
| `PUT` | `/api/categories/order` | `{ categoryIds: string[] }` | `200` `Settings` |

Validation messages: `Name is required`, `A category with this name already exists`, `Enter a color like #1a73e8`
(invalid hex, also for `seedColor`). Colors are normalised to lowercase. `PATCH /api/settings` accepts
`If-Match: <version>` (412 if stale); the web app sends it. Deleting a category does not rewrite Google events: task
lists keep the stale `categoryId` in Google, and the API reports them as `categoryId: null` (calendar color). The
settings endpoints do not touch the provider, so they work during a Google outage.

Filtering by category/tag is done in the web app on the loaded items (no server query parameters). Filter state lives
in the URL query: `categories=<id>[,<id>…]` (`none` = without category) and `tags=<tag>[,<tag>…]`, e.g.
`/week/2026-10-12?categories=shopping,none&tags=weekend`. Categories are OR-ed, tags are OR-ed, and the two groups are
AND-ed. Events are never filtered.

`PATCH /api/prefs/theme` `overrides` also takes the fine-tuning fields (feature theme-menu): `glowStrength` (integer 0..150), `radius` (integer 0..28), `tint` (integer 5..60), `density` (`compact|comfortable|airy`), `checkbox` (`round|square|rounded`), `checkFill` (`filled|outline`), `check` (`tick|bold|cross|dot`), `icons` (`outlined|rounded|sharp|solar|phosphor|pixelart`). Out-of-range or unknown values answer `400`. The same optional fields exist in `calendar-theme/2`.

**Theme preference** (`GET/PATCH /api/prefs/theme`): `{ preset: string; overrides: Overrides; seasonal: 'off' | 'header' | 'all' }`,
stored per person in `prefs.json` under `theme`; default `{ preset: 'Default', overrides: {}, seasonal: 'all' }`.
`preset` is a preset name or `theme:<id>`. `overrides` takes `glow`, `entries`, `corners`, `scene` (the Scene values
above), `seed` (`#rrggbb`) and the fine-tuning fields above; a `PATCH` replaces the fields it sends.
*Migrations on read* (each once, marker in the stored theme): `sceneUnified` — the scene that was visible wins (a
preset or override scene other than `none` stays; otherwise the old settings `scene` becomes the override; the old key
stays in `settings.json`, unused); `seasonalMigrated` — a stored preset `Automatic` becomes `Default` with `all`, an
override scene `season` becomes `header` with the override removed, everything else becomes `off`.

### Imported themes (`/api/themes`)

Per person (their own Google account when sign-in is on), stored in `DATA_DIR/users/<sub>/themes/` (feature theme-import).
A theme is a `calendar-theme/2` document (`shared/theme.schema.json`, no SVG in it) plus
an optional own top bar picture kept next to it.

```ts
type Picture = { light?: string; dark?: string };   // SVG text, each ≤ 100 KB, at least one
```
- `GET /api/themes` → `200` `{ themes: { id: string; doc: ThemeDoc; picture?: Picture }[] }`, oldest first.
- `POST /api/themes` with `{ theme: ThemeDoc; picture?: Picture }` → `201` `{ id; doc; picture?; sanitized: boolean }`.
  The server validates the document and the picture and sanitises the picture's SVG again (what is stored is the

### Summary (year view, month picker dots)

### Open task lists (tray, carry-over)

`GET /api/tasklists/open?today=YYYY-MM-DD&days=30` → `200 { items: TaskList[]; finishedToday: TaskList[] }`. `items`:
task lists with at least one unticked item dated in `[today − days, today]` (inclusive). `finishedToday`: task lists
in the same date window with `completedOn = today` (finished today, shown struck through in the tray). Order of both:
date ascending, then untimed before timed, then time, then title. The web app shows lists dated before `today` as **carried over** on today (and not on their own
date); lists with no open items are never carried, and neither is a list made after its own day had ended (`createdOn` later than `date`; absent `createdOn` = carried). `days` max 90, default 30.

### All open task lists (Tasks view)

`GET /api/tasklists/all-open?today=YYYY-MM-DD` → `200 { items: TaskList[] }`: every task list that is not complete
(a list without items counts as open), undated lists and lists dated in `[today − 365, today + 365]`. Unordered; the
web app groups and sorts. Errors: 400, 502, 503. Undated lists are returned only here and by `GET /api/tasklists/:id`;
`/api/items`, `/api/summary` and `/api/tasklists/open` never return them.

### Archived task lists (Tasks view, Archive tab)

`GET /api/tasklists/archive?today=YYYY-MM-DD` → `200 { items: TaskList[] }`: every finished task list (at least one
item, all ticked), dated or undated: the lists carrying the private marker `done=1` of any age, plus the finished
lists dated in `[today − 365, today + 365]` (lists written before the marker existed). Unordered; the web app sorts
(newest `completedOn` first, lists without `completedOn` last by date). Errors: 400, 502, 503. `all-open` never returns
finished lists; the date-range endpoints are unchanged.

### Ink (handwritten items; feature handwritten-lists)

An **ink item** is a task item with `ink: true` and an empty `title` (a rename is a `400`); its strokes are not in Google
(30 KB limit for private properties). They are stored by item id (ids are unique, so the occurrences of a repeating list
that hold the item share its ink): for a personal list in `DATA_DIR/users/<sub>/ink.json` (taken by the Drive backup), for a
shared list in the list's own document (`ink`), so every member sees and edits the same ink; sharing a list moves its ink
into the list and stopping to share moves it back. `InkDoc` = `{ version: 1, items: { <itemId>: InkStroke[] } }`: the
person's own ink plus that of every shared list they are on. A stroke is `{ p: [x, y, pressure][], c?: '#rrggbb' }` (no `c`
= the theme's text colour); x and y are in line heights from the line's left and top (so the ink scales to any line,
decision G8), pressure 0..1; at most 5000 points per stroke and 500 strokes per request. Google gets the description line
`☐ Handwritten item` (decision A3). The pref `labsHandwriting` (boolean, default `false`) is the
Labs switch. A retired `labsDrawWithFinger` in a stored document or a patch is ignored (finger drawing is unsupported).

| Method | Path | Body | Success |
|---|---|---|---|
| `GET` | `/api/ink` | – | `200` `InkDoc` |
| `POST` | `/api/tasklists` | items may be `{ title: '', strokes }` (ink items; a list of ink items alone needs no title) | `201` the list |
| `POST` | `/api/tasklists/:id/items[?scope=following]` | `{ strokes, id?, index? }` (instead of `title`) | `201` the list, with a new ink item (in every following list with `scope=following`) |
| `PUT` | `/api/tasklists/:id/items/:itemId/ink` | `{ strokes: InkStroke[], base?: string[], at?: number }` | `200` the list; without `base` it replaces the item's strokes (`[]` clears them, the item stays). With `base` (the keys of the strokes the device started from) and `at` (ms) the change is merged with what other devices wrote meanwhile: strokes added are kept, a stroke taken away is gone, a line cleared as a whole removes everything drawn before `at` (an erase mark, a stroke without points, keeps it from coming back); a stroke's `t` (ms) is its identity |

A text item given strokes, or an ink item given a title → `400`; unknown item → `404`; a list holds at most about 1 MB
of ink (`INK_LIST_MAX_BYTES` in `shared/limits`, measured by `inkListBytes` as the JSON of the strokes of each ink item;
the web app uses the same helper) → `413 PAYLOAD_TOO_LARGE` (key `tasklist.inkFull`). A repeated `POST` with the same item
`id` stores the ink once. Deleting an item deletes its ink (not for `scope=this` on one occurrence of a repeating list, which
leaves the item and its ink to the others), deleting a list deletes the ink of its items (an occurrence of a repeating list
leaves it). `GET /api/changes` carries the document as the file `ink` when its version moved. Templates' ink is not yet stored
(open point).

| `POST` | `/api/backup` | Backs up now (forced, no throttle) and answers `200 BackupStatus` with the new `lastBackupAt`. `403 DRIVE_PERMISSION_REQUIRED` without the scope; `502 BACKUP_FAILED` (message = reason) when Drive fails, the status then shows `failed`. |

**Backup bundle** (the Drive file; a restore must read every bundle an older version wrote). One file per backup,
`backup-<sub>-<UTC timestamp>.json` in the person's Drive `appDataFolder`, at most 5 MB:

```ts
interface BackupBundle {
  schema: 1;
  created: DateTime;
  appVersion: string;
  sub: string;                        // the person's Google id
  files: Record<string, string>;      // path relative to DATA_DIR -> UTF-8 content
}
```

`files` holds everything under `users/<sub>/` except `google-token.json` (a secret) and `backup-state.json`; the files
of registered stores under their own top-level folder (`shared/lists/<id>.json` for lists the person owns,
`shared/memberships/<sub>.json` for lists they belong to); and the server-wide files under `server/<path>`. A restore
writes only paths under `users/<sub>/` or a registered folder, and server-wide files only onto a server where every one
of them is still untouched.

### Motivation: check-in streak and plant

Stored server-side per person in `DATA_DIR/users/<sub>/motivation.json` (ADR 0035; migrated from the server-wide file
as described under "Settings and categories"; synced across devices). Dates are local dates of the
app clock (`TZ`).

```ts
interface Motivation {
  streak: { current: number; best: number; lastCheckIn: LocalDate | null; checkedInToday: boolean };
  plant: {
    growth: number;            // total points, never decreases
    stage: 'Seed' | 'Sprout' | 'Small plant' | 'Leafy' | 'Flowering';
    stageIndex: 0 | 1 | 2 | 3 | 4;
    nextStageAt: number | null;
    todayPoints: number;       // points earned today (0–30)
    lastWatered: LocalDate | null;
    flowers: number;           // sunflower count, 0–30
    vitality: 100 | 75 | 50 | 25;
    mood: 'happy' | 'thirsty' | 'dry' | 'droopy';
    message: string;
  };
}
```

| Method | Path | Success |
|---|---|---|
| `GET` | `/api/motivation` | `200` `Motivation` |
| `POST` | `/api/streak/checkin` | `200 { current, best, checkedInToday: true, newToday: boolean, motivation: Motivation }` |

**Streak rules:** the web app calls `POST /api/streak/checkin` once after startup and again when the app becomes
visible on a new local day. If the last check-in was yesterday, `current + 1`; if it was today, unchanged
(`newToday: false`); otherwise `current = 1` (quiet reset). `best = max(best, current)`. Idempotent per day.

**Plant rules** (all server-side, so they cannot be spammed from a client):

| Action | Points | Counted when |
|---|---|---|
| Daily check-in | +10 | first check-in of the day |
| Create event | +5 | `POST /api/events` returns 201 |
| Create task list | +5 | `POST /api/tasklists` returns 201 |
| Tick an item | +2 | an item goes from not done to done; each item id counts at most once per day |

- Daily cap: 30 points (`todayPoints` resets at local midnight). Points above the cap are dropped.
- Stage thresholds on `growth`: Seed 0, Sprout 20, Small plant 60, Leafy 140, Flowering 280.
- Watering sets `lastWatered = today` (any awarded point, even if capped to 0 extra points).
- Mood from `d` = calendar days since `lastWatered`: d ≤ 1 → happy (100); 2 → thirsty (75); 3 → dry (50);
  ≥ 4 → droopy (25, the floor). No `lastWatered` → happy. Growth never decreases; the plant never dies.
- Messages (exact): happy "Your plant is happy", thirsty "Your plant is a little thirsty", dry "Your plant could use
  some water", droopy "Your plant is resting. Anything you do will perk it up."
- Streak and plant points are recorded regardless of the person pref `streak` (it only changes which widget the top
  bar shows); the check-in message shows whatever `streak` is, `off` included.
- **Sunflower field** (the scene of that name) uses the same points and mood: `plant.flowers = min(30,
  floor(growth / 40))`. Flowers never decrease. With `Settings.sunflowers = 'grow'` the field shows `plant.flowers`;
  with `'full'` it shows a fixed 30 and never grows (no `bloom`). The UI shows at most 15 on viewports < 600 px wide
  and up to 30 above that; the accessible label always states the count of the mode ("Sunflower field: 5 flowers",
  singular "1 flower", "Sunflower field: 30 flowers" for the full field). In `grow` mode a newly earned flower (the
  count went up since the last `Motivation` the client saw) plays the `bloom` effect.
- Server-side awarding hooks: the event/task list/item handlers call `MotivationService.award(kind, key)`. Mutation
  responses carry the header `X-Motivation-Changed: 1` when points were awarded, and the web app then refetches
  `/api/motivation`.

### Live updates (`GET /api/events/stream`, ADR 0030; name settled at build) → 200 `text/event-stream`

Needs a session (`401` without). One connection per open app. The server sends the event `changed` whose only data is
the kind of data (`events`, `taskLists`, ...; a content-free nudge, and an event without data would never reach the browser) whenever something changes through the server for that person (events, task lists, settings,
prefs, theme, own themes, templates, Canvas, motivation) or for any member of a shared list, plus a comment line every
25 s to keep proxies from closing it. The app answers a nudge with a changes-since request (`/api/changes`); it
reconnects by itself (`EventSource`) and syncs once after every reconnect. While at least one connection of a person is
open the server asks Google for changes every 20 s and sends `changed` when there are any. Sign-out closes the
person's connections. More than 10 open streams of one person: `429` (the browser then stops retrying; its poll still syncs).

### Diagnostics (`POST /api/diag/sync-error`) → 204

The web app sends this once when it enters the "Can't reach Google Calendar" state. The server only logs it
(`client_sync_error`, ADR 0009); nothing is stored and the response has no body. Needs a session while
sign-in is on. Body (at most 1 KiB, unknown fields → 400):

```ts
interface SyncErrorBeacon {
  kind: 'network' | 'timeout' | 'http' | 'abort';
  status?: number;       // 100-599, the HTTP status for kind "http"
  task: string;          // which refresher failed: items, summary, settings, calendars, a registered task, or "other"; 1-32 of A-Z a-z 0-9 _ . : -
  online: boolean;       // navigator.onLine
  resumed: boolean;      // the page became visible less than 5 s before the failure
  app: boolean;          // Android app (true) or browser (false)
  ageSec?: number;       // 0-604800, set when the beacon could not be sent at once and went out after the next good sync
}
```

At most one beacon per client (session) per minute: a second one → `429 RATE_LIMITED`. The web app ignores every
failure of this call.

### Diagnostics (`POST /api/diag/device-log`) → 204

## Stale data and rate limits (Google provider)

Google limits calls per person. The server caches `events.list` per calendar and range and `calendarList.list` for
25 s (identical concurrent calls share one request; every write makes the cache stale at once) and, once Google answers
`rateLimitExceeded` / `userRateLimitExceeded` / 429, stops calling Google for a cooldown (ADR 0007).
Meanwhile:

- a `GET` that can be answered from the last known data answers `200` with the header `X-Stale: 1`; `GET /api/items`
  also carries `stale: true` in the body. Nothing else about the response changes.
- a request that needs data the server does not have, and every write, answers `503 RATE_LIMITED` with
  `Retry-After: <seconds>`.

## Static files

### `GET /app.apk` (Android app download)

Serves `DATA_DIR/downloads/app.apk` if the file exists: `200`, `Content-Type: application/vnd.android.package-archive`,
`Content-Length`, `Content-Disposition: attachment; filename="calendar.apk"`, `Cache-Control: no-cache`. Without the file
`404` with the usual JSON error body (never the SPA `index.html`). Public (outside `/api`, no session needed: the
file holds no secrets). The file is put there by `scripts/android-build.sh`, not by the server.

`DATA_DIR/downloads/app.json` (`{ "versionCode": 7, "versionName": "1.1.7", "certSha256": "<64 hex>" }`, written next to the APK by `scripts/android-build.sh` once the APK's signer matched the pin in `android/release-cert.sha256`,
`versionCode` = git commit count) is reported by `GET /api/config` as `apk: { versionCode, versionName, certSha256? } | null` (null without a valid
file; Settings shows `certSha256`). The Android app compares it with its installed `versionCode` and offers the download (snackbar "New app version").
`GET /app.json` (public, next to `/app.apk`) answers that sidecar plus `sha256`, the SHA-256 of the file served as `/app.apk` (hashed by the server), with `Cache-Control: no-cache`; `404` with the JSON error while there is no APK.
TEST_MODE: `POST /api/__test/apk { versionCode, versionName }` overrides it until the next reset.

## Sign-in (auth on when `PROVIDER=google`; off with `PROVIDER=mock` unless a test turns it on)

| Method | Path | Effect |

| `GET` | `/api/auth/google/callback?code&state` | Exchanges the code. | `GET` | `/api/auth/google/start?app=1&challenge=<c>` | The Android app's flow (Google refuses OAuth in a WebView, so the app opens this URL in the system browser). Same as without `app`, but the `state` remembers the flag, and `challenge` (required: base64url, no padding, of the SHA-256 of a random verifier the app keeps, RFC 7636 S256; else **400**, so an old APK cannot start a sign-in) travels with the browser in the short-lived `cal_app_challenge` cookie and is stored with the code. On a successful callback the response is a **302** (no `cal_session` cookie, `Cache-Control: no-store`) to `intent://auth?code=<code>#Intent;scheme=lan.mordor.calendar;package=lan.mordor.calendar;S.browser_fallback_url=<URL-encoded /api/auth/app-open?code=<code>>;end`, which Chrome turns into the deep link `lan.mordor.calendar://auth?code=<code>`; when it cannot launch the app it goes to the fallback page. `<code>` is random (128 bit), single-use, valid 60 s, bound to the session just created and to the challenge; a not-allowed address still ends in 302 `/signin?error=private` with no code. Only `app=1` selects this; the browser flow is unchanged. |
| `GET` | `/api/auth/app-open?code` | Public. The fallback of the intent redirect: **200 HTML** with the visible link `#open-app` (`lan.mordor.calendar://auth?code=<code>`) and a script launch; viewing it does not use the code up. An unknown, used or expired code answers 400 (the "expired" page). `Cache-Control: no-store`. |
| `GET` | `/api/auth/app-exchange?code&verifier` | Public. The app's WebView loads it from the deep link, with the verifier only the app holds: a valid code whose challenge is the SHA-256 of `verifier` sets the normal `cal_session` cookie and answers 302 to `/` (`/?calendar=missing` when the calendar scope is missing). An unknown, used or expired code, a missing, malformed or wrong `verifier` (which also uses the code up), or none, answers **400** with a small HTML page ("This sign-in link has expired or was already used", link to `/signin`) and sets no cookie. `Cache-Control: no-store`. Codes are kept in memory only (a restart invalidates them). |
| `GET` | `/api/auth/me` | `{ email, name }` of the signed-in person; 401 without a session; `{ email: null, name: null }` while auth is off (so the client can tell "off" from "signed out"). Public. |
| `POST` | `/api/auth/signout` | Ends the session (server side) and clears the cookie; 204. The optional body `{ endpoint }` is this browser's push subscription, which is deleted with the session (a missing or invalid endpoint does not stop the sign-out). |
| `POST` | `/api/auth/signout-all` | "Sign out everywhere": ends every session of the signed-in person and clears the cookie; 204 (401 without a session). The optional `{ endpoint }` body is as for sign-out. |

Every `/api/*` request while auth is on re-checks `ALLOWED_EMAILS`: a person who was taken off the list gets **401** and loses all their sessions.

All non-GET `/api/*` requests need an `Origin` header that is one of `PUBLIC_URL` / `ALLOWED_ORIGINS` (or none, as the Android widget sends; without a
`PUBLIC_URL` the page's own host is accepted), else **403 `FORBIDDEN`**, and a body must be `application/json` (else **415**; an empty body needs no type, also when it arrives chunked) and at most 256 KB (`POST /api/themes`
400 KB; else **413**).

While auth is on, every other `/api/*` route except `/api/health`, the two OAuth routes and `/api/auth/app-exchange` answers **401
`UNAUTHENTICATED`** without a valid session. When a person's Google refresh fails with `invalid_grant`, the API answers
**401 `GOOGLE_REAUTH`** for that person; the client then shows "sign in with Google again". When the person did not
tick Google's calendar checkbox (granular consent), the callback reads the granted `scope` from the token response
(authoritative; the `scope` query parameter is only a hint), stores it in `google-token.json` next to the refresh token,
signs the person in and redirects to `/?calendar=missing`; calendar calls then answer **403
`CALENDAR_PERMISSION_MISSING`** (stored scope lacks calendar, or Google answers 403 `insufficientPermissions` /
`ACCESS_TOKEN_SCOPE_INSUFFICIENT`, also for tokens stored before the scope was recorded). The client then shows
"grant calendar access". After sign-in and sign-out the server drops that person's cached provider so a new token
applies without a restart. Redirect URI =
`GOOGLE_REDIRECT_URI` (default `${PUBLIC_URL}/api/auth/google/callback`).

## Storage in Google

How a task list is stored as a Google event in the person's hidden tasks calendar (ADR 0006). Other Google clients see
these events, so this encoding is a contract like the REST API above.

| Task list | Google event |
|---|---|
| `title` | `summary` |
| `date`, `time = null` | all-day: `start.date = date`, `end.date = date + 1` |
| `date`, `time = HH:mm` | timed: `start.dateTime = date T time`, `end.dateTime = start + (estimateMinutes ?? 30) min`, `timeZone = TZ` |
| `estimateMinutes` | `extendedProperties.private.estimate` (decimal string; absent = none) |
| `recurrence` (@optional) | Google `recurrence: ["RRULE:FREQ=DAILY\|WEEKLY\|MONTHLY"]`; per-occurrence ticks are stored by patching the instance (Google exception) |
| marker | `extendedProperties.private.kind = "tasklist"` |
| format version | `extendedProperties.private.tlv = "1"` |
| `items` | `extendedProperties.private.items` = JSON `[{"id","t","d"}]` (`t` title, `d` 0/1), chunked: |
| | if the JSON is ≤ 1024 chars it is stored in `items`; otherwise it is split into 1000-char slices stored in `items`, `items_1`, `items_2`, … and `itemsChunks = "<n>"`. Readers concatenate `items` + `items_1..n-1`. Writers delete stale higher chunks (patch them to `null`/empty). |
| human mirror | `description` = one line per item, `☐ title` or `☑ title`, joined with `\n`, nothing else |
| `createdOn` | `extendedProperties.private.createdOn` = `YYYY-MM-DD`, written on create (the input's, else the app clock's today). Absent on older lists. |
| `completedOn` | `extendedProperties.private.completedOn` = `YYYY-MM-DD`, written by `TaskListService` on an update that leaves no open item where one was open before (date from the app clock, so the test clock applies; a list created complete gets none) and removed on the write that leaves an item open again (untick, add). Absent = not complete, or completed outside the app (Google app) or before this property existed. |
| `canvas` (@optional) | `extendedProperties.private.cx` and `.cy`: integer strings `0..10000`, the note's place on the Canvas (the Canvas of the Tasks view); both absent = no place yet |
| undated | a list without a date: all-day on the anchor date **2099-12-31** with `extendedProperties.private.undated = "1"` (below) |
| `categoryId` | `extendedProperties.private.categoryId` (absent = no category) |
| `tags` | `extendedProperties.private.tags` = JSON array of strings (absent or `[]` = none; ≤ 1024 chars by limits) |
| color in Google | `colorId` = nearest Google color to the category color; no category → `colorId` removed (calendar color) |

- Limits: 200 items, 200 chars per title; Google allows max 300 extended properties / 32 kB total, which these limits
  respect (200 × ~215 chars ≈ 43 kB worst case → the server rejects writes whose encoded size exceeds 30 kB with
  `400 VALIDATION_ERROR "Task list is too large"`).
- **Authority**: `extendedProperties` is authoritative. If `kind = tasklist` but no `items` property exists (created
  by hand in Google, or stripped), items are parsed from the description (`☐`/`☑`/`[ ]`/`[x]` prefixes, other
  non-empty lines = not done) and get stable ids derived from line index + title hash; the first app write then
  stores proper `items`. Edits made to the description in the Google app are overwritten on the next app write
  (documented limitation).
- Task lists are excluded from the plain event endpoints and vice versa (404).
- The app shows the category color from settings (exact hex), while Google shows the nearest `colorId`. When a
  category's color changes, Google `colorId`s of existing task lists are updated lazily on their next write (no mass
  rewrite).
